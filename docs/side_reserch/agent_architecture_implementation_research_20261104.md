# Как усилить архитектуру Agent OS: исследование и план

Дата: 2026-11-04. Статус: первый завершённый исследовательский проход; предложения требуют обычного проектирования перед реализацией.

Основание: [ревью и договорённости](./agent_architecture_review_20261104.md). Автоматический стенд оценки — последний этап; на текущем этапе качество оценивает пользователь вручную.

**Уточнённое ограничение:** все роли должны быть работоспособны на недорогих моделях, включая контроллер и синтез. Пользователь назвал MiniMax и «кимчи», предварительно интерпретированное как Kimi. Обязательного сильного агента и автоматического дорогого fallback в целевой схеме нет. Раздел 9 уточняет рекомендации под это ограничение; конкретные model ID и endpoint ещё не выбраны.

Маркировка: **[Р]** — факт репозитория; **[И]** — вывод прочитанного внешнего источника; **[П]** — предложение для Agent OS, которое источник непосредственно не доказывает. Все проектные схемы и шаги ниже с пометкой [П] — эскизы, не уже реализованные контракты.

## 1. Что исследовали и какой подход выбран

**[П]** Сохранить текущий durable runtime и controller/worker модель. Усилить границы данных: проверяемое утверждение → сохранённая ревизия с доказательствами → итоговое представление. Одновременно добавить runtime возможность завершать ожидание по времени. Новые автономные проверяющие агенты сами по себе эти дефекты не исправят.

Вопросы исследования:

1. Как отличить существующую ссылку от ссылки, действительно подтверждающей фразу?
2. Как не потерять подтверждённость при синтезе и кратком пересказе?
3. Как кодом проверять логи и агрегаты, не выдавая совпадение значений за доказательство?
4. Как получить частичный результат при исчерпании времени, сохранив один механизм восстановления?
5. Как улучшать поведение вручную без раннего строительства стенда оценки?

## 2. Что дают первичные источники

**[И] ALCE.** Работа рассматривает генерацию с цитатами и отдельно оценивает корректность ответа и качество цитирования. Это поддерживает разделение проверки содержания и проверки ссылок. Существование ссылки само по себе не устанавливает истинность ответа. [Статья и abstract, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.398/).

**[И] FActScore.** Метод разбивает длинный ответ на атомарные факты и оценивает, какие поддерживаются надёжным источником. Здесь атомарный факт — высказывание, а не просто найденный идентификатор или число. [Статья и abstract, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.741/).

**[И] Temporal.** Контракт ActivityOptions различает полный срок исполнения с повторами (scheduleToCloseTimeout), время ожидания начала (scheduleToStartTimeout) и срок одной попытки (startToCloseTimeout). Это полезный образец раздельной семантики времени. [Официальный TypeScript API](https://typescript.temporal.io/api/interfaces/common.ActivityOptions/).

**[И] Microsoft Durable Task.** Документация предлагает durable timers для задержек и ограничения ожидания асинхронных действий; примеры используют гонку работы и таймера. [Официальная документация](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-timers).

**[И] Anthropic.** Context engineering рассматривает отбор полезной информации при ограниченном контексте, в том числе компактное состояние и получение данных по необходимости. [Инженерная статья](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).

**Граница применимости.** Прочитаны страницы публикаций с abstract и указанные инженерные документы; полного воспроизведения экспериментов статей не было. ALCE и FActScore не доказывают корректность предлагаемого ниже SQL-проверяющего для логов. Документация других runtime не означает необходимость миграции на них. Численных обещаний улучшения качества или стоимости для Agent OS нет.

## 3. Ответ как представление принятых ревизий [П]

### 3.1 Минимальное изменение сначала

Существующий KnownClaim расширить полями проверенной ревизии: claimRevisionId, evidenceIds, coverage. В screenDraft известное утверждение получает эти поля из сохранённой ревизии. Синтез может выбирать порядок и разделы, но не подменять основания.

Для совместимости старого формата проверять draft-ссылки отдельно, но не использовать их как новое основание verified-утверждения. В новой версии вывода модели известный claim задаётся идентификатором ревизии без повторной передачи текста и evidenceIds. Новая формулировка — fresh claim, который проходит обычную проверку.

### 3.2 Воспроизводимость ответа

Ответ фиксирует точные ревизии, а не каждый раз вычисляет latest. Иначе при последующей проверке или follow-up старый ответ меняет смысл без собственной новой версии. Новая проверка создаёт новую ревизию claim и при необходимости новую версию ответа; старое представление остаётся воспроизводимым.

Синтез строится по снимку набора ревизий. Перед записью ответа выбрать явную политику: отклонять публикацию, если значимая ревизия уже заменена, либо сохранять результат как ответ на указанную ревизию состояния с признаком предварительности. Для первого этапа проще повторная проверка актуальности перед записью; не держать транзакцию через LLM-вызов.

### 3.3 Варианты summary

| Вариант | Гарантия | Цена и ограничения |
|---|---|---|
| Выбор claimRevisionId, отображение текстов кодом | Новых фактов на этапе представления нет | Менее свободный стиль; качество исходных claims всё ещё зависит от проверки |
| Свободный summary, затем извлечение и проверка всех фактов | Дополнительное выявление ошибок | Ещё один недетерминированный проход, бюджет и циклы; абсолютной гарантии нет |
| Только усиленный промпт | Намерение модели следовать правилам | Дефект F1 остаётся возможным |

Рекомендация первого этапа: модель выбирает 1–3 ревизии уже прошедших фильтр утверждений. Код выводит их текст и статус; если подтверждённых фактов нет, добавляет фиксированное сообщение о неопределённости. Гипотезы можно показывать в резюме с явной пометкой. Сортировка и соединение фраз не должны добавлять причинные союзы или повышать уверенность.

В режиме model_knowledge все элементы остаются assumed. Сборка summary не превращает знания модели в установленные факты.

## 4. Проверяемые высказывания вместо списка значений [П]

### 4.1 Небольшой закрытый набор

| Тип | Что фиксирует кандидат | Что проверяет код |
|---|---|---|
| observation | источник, snapshot, совместный фильтр, record selectors | Предикат выполнен на одной записи либо заданной связи |
| aggregate | область данных, metric, operation, unit, ожидаемое значение | Точный результат допустимой агрегации для указанной области |
| comparison | две совместимые области, метрика, операция сравнения | Обе величины, единицы, знаменатель, правила null и деления на ноль |
| hypothesis | предположение и поддерживающие/противоречащие ревизии | Только валидность ссылок и доступность оснований; причинность не объявляется доказанной |

Модель не выдаёт произвольный SQL или исполняемое выражение. Она заполняет закрытую схему, сервер строит разрешённый запрос. Это продолжает ADR-0005.

Пример проверяемого факта: «В snapshot S у payments за [t0,t1) найдено 42 timeout-события». Структура должна задавать `count`, фильтр `service=payments AND event=timeout`, интервал, snapshot, единицу `events`. Просто service=payments и number=42 этого не выражают.

### 4.2 Связь структуры и текста

Даже хорошая структура не доказывает свободную фразу, если модель сопроводила корректный count причинным выводом. Для observation/aggregate/comparison первого этапа отображаемый текст лучше получать шаблоном из проверенной структуры. Свободную интерпретацию хранить отдельно как гипотезу.

### 4.3 Полнота и отрицательные выводы

Разделить «нашли событие» и «событий не было». Для первого достаточно конкретной записи. Для второго нужны полный охват заданной области, согласованный snapshot и отсутствие усечения. При sample/failed fetch/unknown total результат — insufficient для утверждения об отсутствии. Сравнение требует совместимой семантики областей; изменение snapshot само по себе не делает любое сравнение недопустимым, но должно быть явно описано.

У интервалов определить границы, например [start,end), временную зону и отказ на невалидной дате. У чисел различать count, rate и duration; не искать просто совпавшее число в любом bucket.

### 4.4 Что делать с прежними supported

Не усиливать задним числом смысл существующего статуса. Добавить версию/метод проверки, например legacy_atom_match и predicate_v1. Старый ответ сохраняет историческую версию. При новом использовании старого claim показывать прежнюю ограниченную степень проверки либо перепроверять. Автоматически переносить старый supported в новый строгий established нельзя.

Полный knowledge graph и универсальный язык доказательств для этого этапа не нужны. Сначала поддержать реальные формы логов и агрегатов fixture, затем обобщать по запросам пользователя.

## 5. Время: прекратить исследование и успеть сохранить результат [П]

### 5.1 Два срока

- researchStopAt — после него не начинаются новые LLM/MCP-запросы исследования; активные вызовы получают отмену.
- finalizeBy — срок, в пределах которого работающий runtime старается записать частичный результат кодом без нового LLM-вызова.

Срок задачи при первом захвате: минимум прежнего `claimTime + deadlineMs` и необязательного абсолютного `expiresAt`. Очередные задачи с истёкшим expiresAt тоже завершаются без внешнего вызова. Старые задачи без поля сохраняют прежнюю семантику.

Не менять молча смысл существующего deadlineAt. Поле TaskSpec, схема БД, проверка приёма, claim и sweeper должны согласованно поддерживать абсолютный предел. Решить, входит ли expiresAt в дедупликацию: нельзя подписать новый запрос с более ранним сроком на задачу, которая его не соблюдает. Политику для совпавшего ключа и разных сроков зафиксировать до реализации.

### 5.2 Durable wait

Эскиз расширения: `waitFor: TaskId[]` плюс `wakeAt?: timestamp`, условие пробуждения — все задачи terminal **или** наступил wakeAt. В БД хранится само условие. Таймер в памяти может ускорять пробуждение, но sweeper после рестарта обязан найти наступившее время.

Один путь перехода waiting → queued с проверкой состояния/версии используется для завершения зависимости и для таймера. Событие пишется в той же транзакции. Если оба условия сработали одновременно, получается один логический переход. Соблюдать уже установленный порядок блокировок runtime.

### 5.3 Частичный ответ и перегрузка

После пробуждения контроллер проверяет время и собирает ответ из сохранённых ревизий. Незавершённые задачи дают ограничения охвата. Финализация идемпотентна; поздний результат старой попытки не меняет опубликованный ответ.

Один таймер не решает голодание очереди. Для постоянно занятого пула рассмотреть отдельную ёмкость для короткой финализации или её повышенный приоритет с ограничением, чтобы не блокировать остальные задачи. Значения выбрать по реальным прогонам.

Для простоя дольше finalizeBy нужен отдельный путь восстановления частичного ответа после терминального deadline контроллера: идемпотентная задача финализации, поставленная транзакционно через существующий outbox, с собственным attempt guard. Обычный контроллер уже не может писать после своего terminal. Такой механизм не восстанавливает отменённое пользователем или удалённое расследование.

Гарантия должна быть честной: при доступных БД и воркерах — завершение в заданном окне; после полного простоя — восстановление результата, а не обещание ответа в прошлом. Отмена внешнего запроса не доказывает, что провайдер прекратил работу или расход.

## 6. Контекст и ручная доводка [П]

Сохранить агентов без скрытой памяти. Каждый вызов контроллера получает компактный актуальный снимок: цель, критерии готовности, ветки, последние значимые утверждения и противоречия, остаток бюджета, допустимые действия. Delta дополняет этот снимок. Исходные данные доступны через идентификаторы evidence и ограниченные выборки.

Отказ по бюджету, отсутствие допустимого действия и переход к частичному ответу можно делать кодом. Исследовательские решения с несколькими разумными вариантами остаются у модели.

Для ручного прогона достаточно заметки:

```text
investigationId / processVersion:
Вопрос и что ожидалось:
Что в ответе верно:
Что неверно или не доказано:
Какие данные или важные оговорки пропущены:
Где агент ходил по кругу:
Стоимость / длительность, если важны:
Следующая одна правка:
```

Это не обязательная форма и не новый продуктовый экран. Пользователь может оставить пару строк. Автоматизацию накопленных примеров обсуждать в самом конце.

## 7. Пакеты изменений и проверка реализации [П]

| Шаг | Основные места | Условие готовности |
|---|---|---|
| A. Сохранить основания | engine/answer/reference-gateway, synthesize.handler, модель ответа | Подмена draft evidence не меняет проверенное основание; ответ хранит точную ревизию |
| B. Безопасное summary | схема синтеза, composeAnswer, code-answer, промпт | Удалённый claim не остаётся в summary; неопределённость сохраняется |
| C. Строгие claims | claims schema/repository, verify, source descriptors, миграции | Раздельные записи не подтверждают совместное событие; числа имеют метрику и область; старые статусы не усиливаются |
| D. Абсолютное время | contracts, db, runtime scheduler/dispatcher/sweeper, engine controller | Ожидание очереди не продлевает срок; таймер переживает рестарт; гонки не дублируют финализацию |
| E. Ручная настройка | ProcessConfig, ContextBuilder, журнал вызовов | Пользователь оценивает реальные ответы и выбирает следующую правку |
| F. Стенд оценки | определить позже | Только после предыдущих этапов и отдельного решения пользователя |

Точечные тесты при реализации A–D: неправильный evidence того же расследования; refuted claim в summary; service/event из разных записей; совпадающее число не той метрики; неполная выборка для отрицания; гонка completion/timer/cancel; рестарт между наступлением wakeAt и доставкой события; отсутствие вызова после expiresAt; повтор финализации после сбоя. Это проверки конкретных контрактов, не ранний benchmark моделей.

## 8. Что ещё предстоит проверить

1. Сколько существующих UI/DTO-потребителей затрагивают новые поля ревизии и структуры summary — перед реализацией A/B составить карту вызовов.
2. Какие реальные вопросы пользователя не выражаются observation/aggregate/comparison — расширять типы только по ним.
3. Как выделить финализацию в текущей модели лимитов, отмены и доставки, не создав обход fencing — отдельный design для D.
4. Нужен ли свободный пересказ вообще, если компактный выбор проверенных формулировок окажется достаточно удобным.
5. Стоимость и полезность каждого LLM-прохода на реальных данных — пока неизвестны; внешние статьи не заменяют ручной прогон Agent OS.

## 9. Архитектура под недорогие модели: MiniMax / предположительно Kimi

### 9.1 Изменение исходного предположения [П]

Проектировать нужно не только дешёвых воркеров, но весь цикл без обязательной сильной модели в центре. Устойчивость достигается уменьшением сложности одного решения и проверками среды. Множество одинаковых слабых проверяющих не дают независимого доказательства: они могут повторить одну ошибку.

Это не означает фиксированный конвейер вместо исследовательского контроллера. Модель по-прежнему выбирает направление поиска, подвопрос и необходимость новых данных. Код ограничивает возможные действия, задаёт точную семантику инструментов и обеспечивает завершение.

### 9.2 Кто что делает [П]

| Компонент | Задача недорогой модели | Ответственность кода |
|---|---|---|
| Планирование | Предложить ближайшие подвопросы | Ограничить количество, бюджет и зависимости; не требовать полный план заранее |
| Контроллер | Выбрать одно из допустимых действий и заполнить небольшой набор полей | Рассчитать admissible, проверить аргументы, отсечь повторы, применить бюджет и дедлайн |
| Воркер | Извлечь кандидаты фактов из ограниченного фрагмента по одному подвопросу | Подготовить выборку, сохранить snapshot/coverage, проверить структуру |
| Проверка | При необходимости предложить, каких данных не хватает | Проверить предикаты и агрегаты; отделить гипотезы от доказанных фактов |
| Синтез | Выбрать релевантные ревизии и порядок | Сохранить их текст, основания и статус; собрать безопасный краткий вывод |

Не дробить каждую операцию на отдельный LLM-вызов автоматически: лишние переходы увеличивают время и суммарную стоимость. Разделение полезно там, где ручные прогоны показывают, что один вызов не справляется с несколькими обязанностями.

### 9.3 Контекст и вывод [П]

- Один вызов — один явно сформулированный результат. Воркеру не поручать одновременно искать данные, доказывать причинность, планировать продолжение и писать отчёт.
- Контроллеру передавать короткий актуальный снимок и только релевантные инструменты; ранжирование не должно скрывать необходимые ветки без возможности получить дополнительные данные.
- Размеры пакетов подбирать снизу вверх на ручных прогонах, а не заполнять рекламируемое максимальное окно модели. Пока нет основания фиксировать универсальные 8k/16k или иной предел для всех ролей.
- Схемы вывода делать небольшими, с явными типами и ограниченными перечислениями. После разбора обязательно проверять семантику в коде, даже если endpoint обещает строгий JSON.
- При невалидном ответе — ограниченный повтор с конкретным сообщением о дефекте и собственным резервом; затем уменьшение задачи либо partial/insufficient. Не вводить бесконечное самоисправление или скрытый переход на дорогую модель.
- Для рутинных переходов (исчерпан бюджет, новых данных нет, наступило время финализации) LLM не нужен.

### 9.4 Практический барьер: текущая интеграция Anthropic [Р]

В [engine.module.ts](../../apps/api/src/engine/engine.module.ts) сборка использует AnthropicTokenCounter и resolveModel. [anthropic-token-counter.ts](../../packages/engine/src/model/anthropic-token-counter.ts) обращается к `/v1/messages/count_tokens`, отправляет заголовки и форму схемы Anthropic. [token-counter.ts](../../packages/engine/src/model/token-counter.ts) предполагает счёт входа с native json_schema. Дизайн KD-7 привязан к модели AI SDK Anthropic и конкретной форме структурированного вывода.

Следовательно, замены строки model в ProcessConfig для перехода к другому провайдеру недостаточно. Порты уже есть — сначала адаптировать их, не менять runtime и хранилище задач.

### 9.5 Что известно о совместимости и что ещё проверить

**[И]** Официальная карточка Kimi K2 Thinking описывает tool calling и доступ через OpenAI/Anthropic-совместимые API. Это свидетельство возможностей конкретной модели, а не подтверждение поведения всех Kimi или всех посредников. [Карточка Moonshot AI](https://huggingface.co/moonshotai/Kimi-K2-Thinking/blob/main/README.md).

**[И]** Официальная страница MiniMax указывает интеграцию с инструментами через совместимые протоколы. Она не устанавливает полную эквивалентность endpoint Anthropic count_tokens или строгих схем вывода. [Страница MiniMax](https://platform.minimax.io/subscribe/coding-plan).

**[П]** Для выбранной пары model + endpoint нужна небольшая проверка адаптера: структурированный ответ, семантика ошибок, отмена, usage, выходной лимит, reasoning-токены и число фактических запросов на один вызов. Это интеграционная проверка совместимости, не отложенный стенд оценки качества.

Профиль возможностей должен различать strict JSON Schema, JSON mode, tool arguments и текстовый JSON; считать их одинаковой гарантией нельзя. Если native schema не поддерживается, адаптер выбирает доступную форму и возвращает данные в ту же серверную схему валидации. Mastra можно оставить, если эта конкретная связка проходит проверку; смена фреймворка не является предварительным условием.

Для TokenCounter: использовать счёт провайдера или подходящий токенизатор с учётом реального шаблона сообщения. Если доступна лишь оценка, явно помечать её как estimate и пересмотреть обещание верхней границы резерва: коэффициент запаса сам по себе её не доказывает. Строгий бюджет требует подтверждённой границы входа и выхода; reasoning/usage обрабатываются по семантике конкретного endpoint.

### 9.6 Обновлённый ближайший порядок [П]

1. Уточнить конкретный model ID и endpoint при подключении; без них не выбирать тариф, SDK или параметры reasoning наугад.
2. Подготовить минимальный совместимый адаптер моделей и счёта токенов; параллельно по смыслу сохранить задачи A/B по доказательствам и summary, не вводя зависимость от сильного синтезатора.
3. Сделать контроллер выбором ограниченного действия, а воркера — исполнителем узкого подвопроса; проверить существующие промпты на лишние обязанности.
4. Реализовать строгую проверку фактов и завершение по времени из C/D.
5. Доводить роли на реальных вопросах по ручной оценке пользователя. Автоматический стенд по-прежнему в конце.
