## Как шёл прогон

- Модель: `anthropic/claude-haiku-5-5`, та же, что в базовом прогоне. Ключ провайдера взят из локального `apps/api/.env` разработчика и записан в базу прогона через API администратора.
- База: чистый Postgres в отдельном контейнере, созданный для прогона и удалённый после него. База разработчика и её серверы `logs`, `backoffice`, `tracker` не тронуты. Серверы фикстуры зарегистрированы заново командой `seed:mcp`, поэтому обновлять списки инструментов не понадобилось (шаг 1 процедуры владельца в базе разработчика не выполнялся).
- API: `node --disable-sigusr1 dist/main` из сборки текущего кода (commit `e82b40d`), порт 4010. Фикстура: порт 4110, снапшот `fx-v1-57187f97` — тот же, что в базовом прогоне.
- Пользователь: администратор `admin` с встроенной ролью; права на три сервера и модель выдал `seed:access`.
- Каждая задача — новая беседа: `POST /api/threads`, одно сообщение, опрос `GET /api/threads/:id/history` до статуса `idle`. Формулировки взяты дословно из базового отчёта.
- Числа: `app.runtime_model_calls` по `task_id` корня беседы, `app.agent_code_calls` (аудит вызовов из кода), история беседы. Время — `runtime_tasks.created_at` → `updated_at`.
- Эталон: одноразовый скрипт вне репозитория считает значения прямо по генератору фикстуры (`trackerTickets()`, `createLogDataset('v1')`, `backOfficeOf()`), без MCP и без модели.

**Проверка до платных вызовов.** Провайдер `anthropic` сначала указывал на локальную заглушку, которая записала запрос к модели и ничего не стоила. В записанном запросе 16 инструментов; блок `Result structure (structuredContent):` есть в описаниях ровно четырёх: `mcp__tracker__search_tickets`, `mcp__backoffice__search_orders`, `mcp__backoffice__get_order`, `mcp__logs__get_trace`. Пример:

```text
mcp__logs__get_trace
Get every log record of one trace (traceId: 32 lowercase hex characters) in time order.

Result structure (structuredContent):
{ records: { ts: string, event: string, level: "debug" | "info" | "warn" | "error", status: "ok" | "error" | "timeout" | "late", message: string, service: ..., spanSeq: integer, traceId: string, durationMs: number }[], snapshot: string, totalMatched: integer }
```

После проверки адрес провайдера вернули к стандартному и записали настоящий ключ.

## Задача 3. Сопоставление заказов и трасс по `traceId`

**Что сделал агент:**

1. Прямой вызов `search_orders` (`status: failed`, окно 6 часов) — 16 заказов. Это получение списка, а не разведка формата; такой же шаг был и в базовом прогоне.
2. Один запуск `run_code`, класс `read`: для каждого из 16 заказов `mcp__backoffice__get_order`, затем `mcp__logs__get_trace` по `traceId` платежа и выбор записи `provider.response`. Всего 32 вызова из кода, все `success`. Скрипт сразу обратился к `order.payments[].traceId` и `records[].event` / `durationMs` — к полям из формы. `runId`: `toolu_01Wn3FbfZNDMXb1A8GQupYG9`, попытка 1.
3. Ответ: итоги и таблица 16 заказов.

Разведки нет: ни запуска `run_code`, чтобы увидеть `traceId`, ни запуска, чтобы увидеть структуру трассы, ни прямого `get_trace`. В базовом прогоне на это ушло два запуска и один прямой вызов.

## Как читать результат

- **Все три критерия PRD выполнены**, и оба ответа верны. Поведение совпало с тем, ради чего делалась фича: модель пишет итоговый скрипт с первого раза, потому что видит имена полей результата в описании инструмента.
- **Это один запуск на задачу — единичный образец, не статистика.** Базовый прогон тоже был одним запуском. Модель не детерминирована: в другой раз она может снова начать с прямого вызова или разведки. Чтобы говорить о частоте, нужны несколько повторов каждой задачи.
- **Сравнение не чистое.** Между базовым прогоном (2026-11-14) и повтором платформа изменилась не только этой фичей: другой набор встроенных инструментов (16 в запросе), другие инструкции агента, большие результаты теперь хранятся по ссылке, права и провайдеры живут в базе. Часть выигрыша в токенах могла прийти оттуда. Прогона на том же коде с выключенными формами не было, поэтому долю самой фичи выделить нельзя.
- **Что можно приписать форме с большей уверенностью:** исчезновение разведки в задаче 3. Оба разведочных запуска базового прогона были нужны только затем, чтобы увидеть `traceId` в ответе `get_order` и структуру записей `get_trace`; теперь эти поля написаны в описаниях, и скрипт использует именно их.
- **Что приписать труднее:** отказ от четырёх прямых `search_tickets` в задаче 2. Форма могла помочь (видно `nextCursor` и поля тикета), но это и выбор стратегии, на который влияют инструкции агента.
- Описания четырёх инструментов стали длиннее на 290–480 символов каждое. На фоне запроса около 8 тыс. токенов это незаметно и окупилось в обеих задачах.

## Чего прогон не проверяет

- Устойчивость: один запуск на задачу, одна формулировка.
- Вклад фичи отдельно от прочих изменений платформы.
- Задачи 1 и 4 базового прогона, обрезанные формы (длиннее 1 500 символов) и серверы без объявленной формы.
- Обновление списков инструментов у серверов базы разработчика (шаг 1 процедуры владельца): там формы появятся только после обновления в панели администратора.
