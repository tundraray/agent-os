## Snapshot

**Overview.** План даёт платформе агента — запуск, который работает над заданием ходами и вызывает инструменты, исполняемые кодом движка (`design-agent-core.md`). Порядок задан зависимостями. Сначала пробный запуск проверяет главное допущение KD-1: Mastra делает ровно один запрос с инструментами без исполнения. Затем идут расширения контракта runtime, миграция, строительные блоки движка (схема, окно, реестры, ход модели), хранилища и инструменты, затем окно по посчитанному входу хода (дизайн 1.6.1: оценка делителем `BYTES_PER_TOKEN`, отказ шлюза `window_exceeded`, сбой `context_overflow`) и обработчик запуска с кодом процесса формы. После этого обвязка тестов и пробный процесс `agent-probe` наполняют интеграционные и сквозные тесты, `apps/api` получает настройки и проверку запаса при старте, а последняя фаза — гейт качества.

**Подход — hybrid.** Фазы 1–3 горизонтальные: на допущении KD-1, новом виде итога runtime и таблицах стоит всё остальное. Фазы 4–6 — снизу вверх внутри движка: чистые блоки, потом хранилища и инструменты, потом обработчик; каждый блок закрывается своими модульными и репозиторными тестами. Фаза 7 проверяет всю часть сценариями на пробном процессе, Фаза 8 подключает `apps/api`, не меняя v2. Пункт (4) задания разбит на Фазы 4–6, чтобы цепочка зависимостей внутри фазы не превышала трёх задач; исключение — Фаза 6 после T6.0 (см. схему зависимостей).

- **Не меняется**: расследование v2 и всё, что видит сотрудник; набор процессов `apps/api` (`ENGINE_PROCESSES` = только v2); схема формы ролей `ProcessConfigSchema`; обработчики v2 и их checkpoint; закрытие расследования по ADR-0006; правило дедупликации runtime.

Каталог файлов задач удалён после переноса их сведений в Notes 8–10.

## Правила выполнения (действуют для каждой задачи)

1. **Окружение.** Postgres — `POSTGRES_PORT=5433 pnpm db:up`, `DATABASE_URL=postgres://agent:agent@localhost:5433/agent_os`. Наборы с Postgres запускаются по одному: `@agent-os/db`, `@agent-os/runtime`, `@agent-os/sources`, `@agent-os/engine` и наборы `apps/api` никогда не идут параллельно против одной базы. `psql` на хосте нет: запросы операционных проверок идут через `docker compose -f infra/docker-compose.yml exec -T postgres psql -U agent -d agent_os -c "..."`.
2. **Настоящая модель не вызывается.** Тесты, CI и операционные проверки идут на модели-заглушке (`MockLanguageModelV4` из `ai/test`, двойник `test/support/scriptedModel.ts`). Единственный вызов настоящей модели — T1.2, его ведёт оркестратор (одобрено владельцем 2026-11-08, Notes 7); стоимость не больше $0.05. Исполнитель задач T1.2 сам не запускает. Счётчик токенов провайдера `count_tokens` (бесплатный, модель ответа не строит) зовётся одним запуском скрипта замера, не больше шести запросов, — замер делителя `BYTES_PER_TOKEN` в T6.0 (решение владельца 2026-11-08, дизайн 1.6.1); тесты, CI и операционные проверки его не зовут.
3. **«Модель оценивает, алгоритм решает».** Код решает только проверяемое без понимания текста: есть ли инструмент в определении, проходят ли аргументы схему, помещается ли вызов в долю и пределы, принадлежит ли ссылка расследованию. Правило окна убирает результаты по возрасту и размеру. Поиск подстроки, ключевого слова или регулярное выражение по тексту модели или записей в любом файле задачи — дефект; исполнитель проверяет свой дифф перед закрытием задачи. Коды, которые пишет движок (`tool_not_in_definition`, `budget_exhausted` и т. д.), тесты сравнивают как литералы из дизайна.
4. **Рабочее дерево.** Исполнитель работает поверх рабочего дерева, чужие правки не откатывает, `git stash` и `git checkout -- <файл>` не применяет. Доказательство «файл не изменился» — sha256 в начале и в конце задачи, записанный в Progress Tracking.
5. **Коммиты.** Стратегия `manual`: исполнитель не коммитит; задача заканчивается в состоянии «готово к коммиту», коммит делает владелец по своей просьбе. Сообщение коммита — английский, Conventional Commits, без `Co-Authored-By` и других упоминаний Claude.
6. **Гейты задачи** (все — ноль ошибок):
   - `pnpm turbo typecheck lint test --filter=<пакеты задачи>`;
   - для `apps/api` — ещё `pnpm --filter api exec prettier --check "src/**/*.ts" "test/**/*.ts"`;
   - задача, которая добавляет или наполняет тест в `test/**/*.e2e-spec.ts`, — ещё `test:e2e` своего пакета (для `apps/api` — скрипт, названный в задаче).

   В конце каждой фазы: полный `pnpm turbo typecheck lint test`; `KNIP_DISABLE_RAW_TRANSFER=1 pnpm knip`; наборы Postgres из операционной проверки фазы, по одному.
7. **Скелеты `it.todo`.** Кейс наполняется по своим комментариям (Given/When/Then, Catches); превращать todo в пустую заглушку запрещено. Ожидаемые значения — литералы. Postgres, runtime и движок не мокаются; двойники — только граница модели, часы и названные в шапке скелета точки обвязки. Скелеты сгенерированы по дизайну 1.2, а план — по 1.6.1: **где комментарий скелета расходится с текстом задачи, действует текст задачи** (расхождения перечислены в T7.2–T7.5).
8. **Кейс наполняется только поставленным поведением.** Перед наполнением исполнитель сверяет каждое утверждение строки, в том числе отрицательное («вызова нет», «строки нет»), с тем, что поставляет эта задача или более ранняя. Если поставляет более поздняя — кейс не наполняется, исполнитель эскалирует.
9. **Изоляция тестов.** Уникальные `resourceId` и `launchKey` на тест (`test/support/new-user.ts`), без truncate. Runtime и пулы закрываются в `afterAll`, `cancelStarted()` вызывается в `afterEach`.
10. **Файлы вне Target Files** не меняются; без этого задачу не выполнить — эскалация (`out_of_scope_file`). Новые файлы названного компонента внутри названного каталога допустимы, имена новых файлов рабочие. Строка «только если требует проверка типов» значит: файл меняется ровно настолько, насколько этого требует `typecheck`.
11. **Границы пакетов (ADR-0004).** Пакеты не читают `process.env`; настройки `AGENT_*` читает только `apps/api`. Модуль агента (`packages/engine/src/agents/`) не импортирует `controller`, `workers`, `verify`, `answer`, `capabilities`. `@agent-os/runtime` не знает ни агентов, ни Mastra. `composeEngine` не экспортируется из `packages/engine/src/index.ts`.
12. **Логи.** В лог попадают только идентификаторы, коды и статусы. Задания, заметки, сессии и промпты в лог не пишутся.
13. **Зависимости.** Новых npm-зависимостей нет: `@mastra/core` 1.80.0, `ai` 7.0.148 (`ai/test` для двойника) и `fast-check` уже есть.
14. **Риск-задачи и ревью тестов.** Пометка «риск-задача» стоит только у задач, которые трогают обвязку и двойники, матрицу рестартов, конкурентность или отмену: T7.1, T7.2, T7.3, T7.4, T7.5. Только они проходят отдельное ревью интеграционных тестов (`integration-test-reviewer`). Аудит всего набора тестов части — один раз, в T9.1 (`test-auditor`).
15. **Доказательство охраны.** Для каждого наполненного INT- и E2E-кейса исполнитель один раз ломает охрану, которую называет строка «Ловит» задачи, видит красный прогон, возвращает код и записывает это в Progress Tracking.
16. **v2 остаётся зелёным.** Каждая задача, которая трогает общий код движка (`create-engine.ts`, шлюз, журнал, транскрипты, загрузку конфигурации, `engine.ts`), в конце прогоняет `pnpm --filter @agent-os/engine test:e2e` целиком: наборы `deep-research-engine` и `agent-quality` проходят без правок своих ожиданий. Известная нестабильность `deep-research-engine.e2e-spec.ts` E2E-1: перед разбором красного прогона повторить один раз и записать оба исхода в Progress Tracking.

## Implementation Phases

### Phase 1: Пробный запуск хода Mastra (KD-1)
**Purpose**: проверить до любого кода части, что один `Agent.generate` с инструментами без `execute` и `maxSteps: 1` делает ровно один запрос к провайдеру и не исполняет ни одного инструмента; при отказе выбрать запасной путь структурного выхода.

#### Tasks
- [x] **T1.1: Ход модели с инструментами без исполнения — проверка на модели-заглушке** — covers DD KD-1, Risks «Mastra не делает один запрос», Building-block `createRoleAgent` (extended)
  - Что: в `role-agent.ts` появляется клиент хода агента рядом с `mastraRoleModelClient`: новый `Agent` на каждый ход, без `Memory`, без `agents`, инструменты определения со схемами и без `execute`, `maxSteps: 1`, `toolChoice` (на последнем ходе — только `finish`), `providerOptions` с метками кэша на системном блоке и последнем сообщении. Клиент возвращает вызовы инструментов (имя, аргументы, идентификатор вызова), текст и `usage`.
  - Тест (модульный, `MockLanguageModelV4` с подсчётом `doGenerate`): «ход с инструментами делает один запрос к модели и возвращает вызовы, не исполняя их» — строки таблицы: ответ из двух вызовов; ответ текстом без вызова; `toolChoice` только `finish`; метки кэша дошли до модели на системном блоке и на последнем сообщении. Доказывает KD-1 (один запрос на ход) и форму ответа хода.
  - Если хоть одна строка не проходит (второй `doGenerate`, вызов `execute`, потеря вызовов): исполнитель останавливается, записывает исход в Progress Tracking и эскалирует; оркестратор переводит T4.3 на запасной путь — структурный выход со списком действий и аргументами строкой JSON (как `ModelArgsSchema` у controller), остальной план не меняется (KD-1).
  - Target Files: `packages/engine/src/model/role-agent.ts`, `packages/engine/src/model/role-agent.spec.ts`
  - Зависимости: нет. Уровень проверки: L2.
- [x] **T1.2: Один настоящий запрос (процедура владельца, платно, не дороже $0.05)** — covers DD KD-1, Risks «Mastra не делает один запрос»

### Phase 2: Контракт runtime — `yield`, причина сбоя ожидаемой задачи, экспорт ключа
**Purpose**: дать runtime три расширения из дизайна, не научив его агентам.

#### Tasks
- [x] **T2.1: Вид итога `yield` → исход `released`** — covers DD KD-6, Contract «Изменения контракта runtime» (`HandlerResultSchema`), UC-E8 (runtime-половина)
  - Что: `HandlerResultSchema` получает `kind` `yield` без обязательных полей `failure` и `waitFor`; `outcomeOfResult` переводит его в `{kind:'released'}`. Ветка `released` в `outcomeWrite` уже есть: задача возвращается в `queued`, счётчики попытки переносятся (`settleAttemptCounters`), `recovery_count` не растёт, итог не пишется. Запрос отмены, пришедший до итога, по-прежнему превращает исход в `cancelled`.
  - Тесты:

## Verification Strategy

- **Correctness definition and method**: агент корректен, когда (а) каждый ход — ровно один вызов модели под резервом и одна строка журнала; (б) каждый эффект инструмента и его итог записаны вместе или не записаны, и после рестарта ничего не исполняется дважды; (в) дерево живёт в задачах одного расследования и останавливается одним переходом; (г) ни один вызов не выходит за долю и бюджет. Чистые правила (окно, ход, доли, причины, загрузка) доказываются табличными модульными тестами; записи — repo-спецификацией на настоящем Postgres; сборка правил — пятью INT на настоящем runtime и одним E2E с убитым процессом.
- **Early verification point**: T1.1 — один `doGenerate` на ход с вызовами без исполнения; критерий успеха — все строки зелёные, T1.2 подтверждает на провайдере одним HTTP-запросом. При отказе T4.3 идёт через структурный выход (KD-1), план не перестраивается.
- **Output comparison**: v2 не заменяется; сравнение — наборы v2 (движок и `apps/api`) зелёные без правок ожиданий после каждой задачи, которая трогает общий код (правило 16).
- **Proof obligations**: из шапок скелетов — INT-1 (агентный модуль работает без предметной области; одна строка аудита на вызов; один запрос на ход; неизменное начало вида), INT-2 (параллельность, одно пробуждение, обе заметки), INT-3 (ничего после перехода; закрытие отменяет дочерних), INT-4 (доли из настоящего журнала), E2E-1 (ход не теряется и не повторяется, вызов агента не ставит вторую задачу). Плюс INT-5 (атомарность кода формы, принудительный конец; посчитанный вход решает окно — UC-E15), K7–K8 (код формы не повторяется) и категории Failure Mode Checklist.

## Risks and Countermeasures

- **Risk**: Mastra делает больше одного запроса или исполняет инструменты (KD-1).
  - **Impact**: резерв перестаёт стоять перед каждым запросом.
  - **Countermeasure**: T1.1 и T1.2 до любого кода части; запасной путь — структурный выход (Notes 2).
- **Risk**: правка общего кода (шлюз, журнал, загрузка, транскрипты) ломает v2.
  - **Impact**: регрессия поставляемого расследования.
  - **Countermeasure**: правило 16 — полный `test:e2e` движка в каждой такой задаче; Фаза 8 — пять наборов `apps/api`.
- **Risk**: двойник модели с ролью `agent` ломает существующие сценарии ролей.
  - **Impact**: красные наборы v2, ложная регрессия.
  - **Countermeasure**: T7.1 — риск-задача с ревью; роли v2 узнаются по прежнему маркеру схемы выхода, агент — по маркеру системного промпта.
- **Risk**: дочерний процесс E2E не может собрать `composeEngine` из исходников.
  - **Impact**: K7, K8 невозможны без формы `probe_record`.
  - **Countermeasure**: `tsconfig.child.json` с `rootDir: "."` уже компилирует импорты из `src` (обвязка импортирует `../../src/claims/...`); T7.5 включает его в Target Files.
- **Risk**: проверка запаса при старте роняет тестовую загрузку с длинной арендой.
  - **Impact**: красный гейт Фазы 8 из-за загрузки, а не кода.
  - **Countermeasure**: T8.1 перечисляет каждую загрузку `AppModule` и `dist/main.js` и проверяет `RUNTIME_LEASE_MS`.
- **Risk**: слоты диспетчера заняты, когда корень просыпается к сроку (гарантия DC-27 условна).
  - **Impact**: принудительный конец по `not_after` не успевает.
  - **Countermeasure**: по дизайну — `RUNTIME_CONCURRENCY` или `AGENT_DEADLINE_MARGIN_MS`; INT-5 UC-E14 идёт при свободном слоте и доказывает только условную гарантию.
- **Risk**: делитель `BYTES_PER_TOKEN` занижает вход — текст, густой от UUID и чисел, даёт меньше 3 байт на токен.
  - **Impact**: конфигурация проходит загрузку, а посчитанный вход хода не помещается в окно; ход уходит на следующие ступени или запуск кончается `context_overflow`.
  - **Countermeasure**: решает посчитанный вход — запрос больше окна к модели не уходит (T6.0, T6.1, INT-5 UC-E15 в T7.4); T6.0 замеряет делитель на трёх образцах, и если наименьшее отношение меньше 3, значение сначала меняет дизайнер в DC-1 (Notes 8).
- **Risk**: одновременные записи заметок нельзя гарантированно столкнуть из сценария.
  - **Impact**: INT-2 доказывает проводку, а не блокировку.
  - **Countermeasure**: номер из последовательности базы (T3.1) и repo-строка с `Promise.all` и повтором (T5.2).
