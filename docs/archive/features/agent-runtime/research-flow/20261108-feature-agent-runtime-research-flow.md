## Snapshot

**Overview.** План строит процесс глубокого расследования v3 на агентах `agent-core` (`design-research-flow.md` 1.4), переводит на него сервер и удаляет код прежнего процесса v2. v3 — единственная поставляемая версия. Порядок задают зависимости:

1. Фаза 1 даёт данные v3 и записи реестров: инструменты `claims_write`, `plan_write`, `gather`, поле шаблона `{{sources}}` с источниками запуска, объявления трёх форм результата и файл `deep-research.v3.json`, который проходит загрузку `agent-core`.
2. Фаза 2 даёт код форм — проверку утверждения, ответ кодом с причиной остановки, черновик ответа и ворота закрытия.
3. Фаза 3 даёт таблицы групп v3 по паре отпечатков, калибровку проверяющего агента и переход сервера на v3 (T3.6).
4. Фаза 4 учит самопроверку форме агентов.
5. Фаза 5 строит обвязку тестов и наполняет INT-1–INT-3, INT-5, E2E-1, E2E-2; программа самопроверки начинает запускать v3 в T5.7.
6. Фаза 6 должна была записать настоящие ответы v3 и проверить INT-4. Платный прогон T6.2 (2026-11-09) кончился на первом ходе controller и нашёл дефект схемы инструмента; его исправила внеплановая T6.2a. Повтор T6.2 и T6.3 владелец пропустил, поэтому записанного прогона v3 на настоящей модели нет.
7. Фаза 7 удаляет код v2 (T7.0) и проходит гейт качества (T7.1). T7.0 не зависит от исхода T5.8, качества ответов, T6.2 и её бюджетной остановки; от платной T3.5 она зависит только через T3.6.

**Подход — strangler с горизонтальными фазами внутри.** v3 встаёт рядом с v2 через ту же точку старта (`createProcessSet.resolve`): пока сервер загружает только v2, код v3 проверяют тесты. Когда появилась поставляемая таблица групп v3 (T3.5), сервер сразу переходит на `[v3]` (T3.6), а старт без версии берёт наибольшую загруженную. Код v2 до удаления — только регрессионная сетка (правило 14), и T7.0 его удаляет. Внутри части фазы горизонтальные, снизу вверх: данные и реестры, код форм, сборка движка и сервера, самопроверка. Сценарии, которые собирают всё дерево, идут после всех слоёв (Фаза 5).

- **Не меняется**: ответ в беседе и его доставка (`chat-entry`), `engine.lifecycle`, таблицы данных (миграций нет, `research_decisions` и `research_signals` остаются) и механика агента `agent-core`, кроме расширения пути инструмента класса `task` для `gather` (T1.2), поля шаблона `{{sources}}` (T1.5) и необязательного `detail` у отказа закрытия (T2.4). ## Правила выполнения (действуют для каждой задачи)

0. **Старт плана.** Часть `agent-core` закоммичена, её план `completed`, поэтому Фаза 1 начинается после утверждения этого плана владельцем. Исполнитель первой задачи записывает в Progress Tracking HEAD. Если символ из Target Files этого плана называется иначе, исполнитель эскалирует (`out_of_scope_file`) и не переименовывает сам.
1. **Окружение.** Postgres — `POSTGRES_PORT=5433 pnpm db:up`, `DATABASE_URL=postgres://agent:agent@localhost:5433/agent_os`; порт 5432 не используется. Наборы с Postgres идут по одному: `@agent-os/db`, `@agent-os/runtime`, `@agent-os/sources`, `@agent-os/engine` и наборы `apps/api` никогда не запускаются параллельно против одной базы. `psql` на хосте нет: запросы проверок идут через `docker compose -f infra/docker-compose.yml exec -T postgres psql -U agent -d <agent_os|agent_os_self_check> -c "..."`. Перед стартом собранного сервера (`dist/main.js`) **на базе `agent_os`** исполнитель записывает в Progress Tracking число `active` расследований в ней и **не отменяет и не удаляет их** (OQ-4); старты на временных базах этого не требуют. Запрет снимается только на шаге сброса локальных баз в T7.0.
2. **Настоящая модель не вызывается** в тестах, CI и операционных проверках: там работают двойник `scriptedModel.ts` (движок) и программы `selfCheckModels.ts` и `engineScriptedRoles.ts` (`apps/api`). Платных шагов два, оба ведёт оркестратор: T3.5 (калибровка) и T6.2 (запись). Владелец одобрил оба в пределах сумм из этих задач, а T6.2 идёт только после бюджетной остановки. Исполнитель задач их сам не запускает. Ключ `ANTHROPIC_API_KEY` берётся только из `apps/api/.env`; в лог, вывод и Progress Tracking он не попадает.
3. **«Модель оценивает, алгоритм решает».** Код решает только то, что проверяется без понимания текста: указатель, схема, ворота над строками, бюджет, статус по полям оценки, группа по таблице. Поиск подстроки, ключевого слова или регулярное выражение по тексту модели или записей в любом файле задачи — дефект; исполнитель проверяет свой дифф перед закрытием задачи. Коды движка (`pointer_invalid`, `needs_narrowing`, `plan_missing` и т. д.) тесты сравнивают как литералы из дизайна.
4. **Рабочее дерево.** Задачи этой части не коммитятся (правило 5), поэтому исполнитель работает поверх незакоммиченных правок предыдущих задач. Чужие правки он не откатывает, `git stash` и `git checkout -- <файл>` не применяет. Доказательство «файл не изменился» — sha256 в начале и в конце задачи, записанный в Progress Tracking.
5. **Коммиты.** Стратегия `per-feature`: исполнитель не коммитит, задача кончается в состоянии «готово к коммиту», а вся часть — один коммит после проверки всей реализации (post-implementation verification). Сообщение коммита — по-английски, Conventional Commits, без `Co-Authored-By` и других упоминаний Claude.
6. **Гейты задачи** (все — ноль ошибок):
   - `pnpm turbo typecheck lint test --filter=<пакеты задачи>`;
   - для `apps/api` — ещё `pnpm --filter api exec prettier --check "src/**/*.ts" "test/**/*.ts"`;
   - задача, которая добавляет или наполняет `test/**/*.e2e-spec.ts`, — ещё `test:e2e` своего пакета (для `apps/api` — скрипт, названный в задаче).

   В конце каждой фазы — полный `pnpm turbo typecheck lint test`, `KNIP_DISABLE_RAW_TRANSFER=1 pnpm knip` и наборы Postgres из операционной проверки фазы, по одному.
7. **Скелеты `it.todo`.** Кейс наполняется по своим комментариям Given/When/Then/Catches; превращать todo в пустую заглушку запрещено. Ожидаемые значения — литералы. Postgres, runtime и движок не мокаются; двойники — только граница модели, часы, считающий источник и точки обвязки, названные в шапке скелета. Скелеты сгенерированы по дизайну 1.3, а план — по 1.4. **Где комментарий скелета расходится с текстом задачи, действует текст задачи** (расхождения названы в задачах Фазы 5).

Если поставляет более поздняя — кейс не наполняется, исполнитель эскалирует.

## Схема зависимостей задач

Фазы идут друг за другом. Исключения:
- T1.4 можно делать в любой момент до Фазы 7;
- T3.2 не задерживает Фазу 4 и T5.1–T5.5; от неё зависят T3.5, T3.6, T5.8 и T7.1, а через T3.6 — T5.6–T5.8, Фаза 6 и T7.0;
- T5.1–T5.5 (только движок) идут после T3.1, T3.3, T3.4 раньше остальных задач Фазы 4;
- T3.5 (платно) исполняется после T5.2, чтобы правка проверяющего, найденная INT-1, не потребовала второй платной калибровки (правило 12);
- T3.6 (переход сервера) идёт сразу после T3.5: без её таблицы сервер на v3 не стартует;
- T4.3 идёт раньше T4.2: обе правят `run-command.ts`;
- T6.2 (платно) идёт после T3.5: бюджетная остановка читает её фактическую цену;
- T7.0 зависит только от T3.6, Фазы 4 и T5.1–T5.7. В порядке ниже она стоит после T5.8 и Фазы 6 из-за общих файлов обвязки, но их исхода не ждёт: если T5.8 не закончена или запись T6.2 отложена, T7.0 идёт без них.

## Risks and Countermeasures

- **Risk**: Haiku в свободном цикле отвечает хуже (главный риск дизайна).
  - **Impact**: ответы сотруднику хуже, чем сейчас; откат к старому коду — только через git.
  - **Countermeasure**: INT-4 на записанных ответах Haiku (Фаза 6; расхождения формы вызовов Sonnet он не ловит); настоящая модель видит v3 на одном сценарии (T6.2). Правка промптов и пределов — данные, вне плана.
- **Risk**: поставляемые числа v3 не проходят загрузку `agent-core` (наименьший вид, сроки против запаса).
  - **Impact**: v3 не грузится, и `apps/api` не стартует после T3.6.
  - **Countermeasure**: T1.3 проверяет загрузку до любой проводки; T3.6 перечисляет загрузки сервера и их запасы.
- **Risk**: с кодом v2 уходит поведение, которое проверяли только тесты v2 (риск дизайна).
  - **Impact**: регрессия, которую больше ничто не ловит.
  - **Countermeasure**: строки без аналога на v3 переносятся до удаления, итог по каждой строке — в Progress Tracking (T5.7, T7.0); `integration-test-reviewer` и `test-auditor` (T7.1); `recorded-runs-20261108.json` остаётся.
- **Risk**: неполный список Target Files у T7.0 останавливает задачу (автостоп при шести и более файлах вне списка).
  - **Impact**: задача встаёт посреди удаления.
  - **Countermeasure**: Target Files T7.0 собраны разбором импортов от удаляемых файлов; файлы, которые меняются только импортами и типами, покрыты отдельной строкой.
- **Risk**: второй `claims_write` одного запуска молча теряет утверждения (уникальность `(taskId, claimIndex)`).
  - **Impact**: утверждения worker исчезают без отказа.
  - **Countermeasure**: T1.1 продолжает индексы запуска; repo-строка «второй вызов того же запуска».
- **Risk**: путь инструмента-задачи для `gather` ломает `call_agent` (общий код `agent-core`).
  - **Impact**: регрессия дерева агентов.
  - **Countermeasure**: T1.2 добавляет интерфейс рядом с `call_agent`, не меняя его ветку; правило 14 — полный `test:e2e` движка, включая INT и E2E `agent-core`.
