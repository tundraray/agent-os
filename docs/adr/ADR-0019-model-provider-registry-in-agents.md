# ADR-0019 Реестр провайдеров моделей с ключами — таблица `agent_model_providers` пакета `agents`, а каталог, права и квоты остаются в модуле `access` и называют провайдера текстом, без внешнего ключа

## Status

Accepted (2026-11-20). Следует [ADR-0014](ADR-0014-mcp-registry-owned-by-agents.md) и не меняет [ADR-0015](ADR-0015-access-gate-and-model-catalogue.md).

## Decision

Провайдеры моделей переезжают из окружения в базу. Решено: строка провайдера — имя, вид, адрес, ключ и признак «включён» — лежит в таблице `agent_model_providers`, которую читает и пишет только пакет `agents`. Наружу пакет отдаёт операции `Agents.providers`, их зовут контроллеры `apps/api`. `ModelClient` на каждом вызове читает строку провайдера по первой части id модели ([ADR-0018](ADR-0018-model-id-provider-prefix.md)), без кэша, поэтому новый ключ действует со следующего вызова на любом экземпляре API.

Каталог моделей, права, квоты и модели по умолчанию остаются в таблицах `access_*` модуля `access`. Каталог ссылается на провайдера первой частью id модели — текстом, без внешнего ключа на реестр. Когда операции реестра или каталога, которую зовёт контроллер `apps/api`, нужен факт другой стороны, его читает контроллер и передаёт входом операции ([port-module-split.md](../code-system/patterns/port-module-split.md)): вид провайдера при добавлении модели, число моделей провайдера в каталоге (`catalogModels`) при его удалении, готовность провайдеров для «Мой доступ». Агенты во время работы получают факты каталога — модель по умолчанию, модель эмбеддингов — через порт `AccessGate` ([ADR-0015](ADR-0015-access-gate-and-model-catalogue.md)).

Решение исключает реестр в модуле `access`, новый пакет для реестра и внешний ключ через границу.

### Связь с ADR-0014 и ADR-0015

**ADR-0014** (реестр MCP-серверов в `agents`) — образец этого решения. Секрет хранится в пакете, который его отправляет, и не пересекает границу пакета, кроме как в запросе к внешней системе. Пишущая операция возвращает «было» и «стало» без значения ключа, а аудит после неё пишет `apps/api`. Чужая сторона ссылается на запись реестра именем, текстом, как право на MCP-сервер. Отличие одно: удалённый MCP-сервер просто перестаёт что-либо давать по праву, а провайдера с моделями в каталоге пакет не удаляет — число моделей ему передаёт контроллер.

**ADR-0015** (права, квоты и каталог за портом `AccessGate` в `apps/api`) не меняется. Вердикт `AccessGate` не несёт ни состояния провайдера, ни ключа. ADR-0015 отверг каталог в нижнем слое, потому что права ссылались бы в него внешним ключом. Реестр провайдеров — тоже данные администратора в нижнем слое, но на него никто не ссылается внешним ключом, поэтому довод ADR-0015 к нему не относится.

## Context

Сегодня ключ, адрес и модель по умолчанию сервер читает из `ANTHROPIC_API_KEY`, `AGENTS_ANTHROPIC_BASE_URL` и `AGENT_DEFAULT_MODEL` при старте. PRD фичи `model-providers` требует, чтобы провайдеров и ключи задавал администратор в базе, а переменных окружения для них не было ([prd.md](../features/model-providers/prd.md), FR-01, FR-02). Пакет пишет и читает только таблицы своего префикса, не импортирует `apps/api` и получает порты параметрами ([ADR-0004](ADR-0004-agent-framework-packages.md), [code-system README](../code-system/README.md)).

**Почему это архитектурное решение.**

1. **Дорого откатить.** Перенос владельца — это перенос таблицы с живыми ключами и замена операций, которые зовут контроллеры и экраны части `web`.
2. **Связывает за пределами фичи.** Каждый вызов модели, служба эмбеддингов и будущие виды провайдеров берут подключение из этого реестра, а каждая новая связь между каталогом и реестром идёт текстом и фактами, которые передаёт контроллер.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Модель вызывает пакет `agents`, поэтому ключ хранится там, где его отправляют, и не ходит через порт на каждый вызов. Каталог остаётся рядом с правами и квотами, которые на него ссылаются. Чтение строки по первичному ключу стоит доли миллисекунды против секунд вызова модели и укладывается в NFR-02.

### Options Considered

1. **Реестр в модуле `access`, ключ в ответе `AccessGate`**
   - Pros: Каталог и провайдеры в одном модуле.
   - Cons: Ключ ходил бы через порт на каждый вызов, а состояние провайдера смешалось бы с правами.

2. **Новый пакет для реестра**
   - Pros: Своя граница у провайдеров.
   - Cons: У реестра нет второго потребителя, кроме `agents`.

3. **Внешний ключ из `access_models` на `agent_model_providers`**
   - Pros: База не даёт модели остаться без провайдера.
   - Cons: Таблица модуля `access` ссылалась бы на таблицу пакета, хотя каждая сторона работает только со своими таблицами. Связь с реестром MCP уже текстовая (ADR-0014).

4. **Таблица `agent_model_providers` в `agents`, связь текстом, факты передаёт контроллер (выбран)**
   - Pros: Ключ не выходит из пакета, кроме как в запросе к провайдеру. Новый ключ действует со следующего вызова на любом экземпляре. `AccessGate` не меняется.
   - Cons: База не держит связь модели с провайдером. Каждый вызов читает строку провайдера.

## Consequences

### Positive Consequences

- Ключ и адрес правятся из панели без рестарта, и смену видит следующий вызов на любом экземпляре API
- Ключ хранится и читается в одном пакете; API отдаёт только признак и последние четыре символа

### Negative Consequences

- Ссылочной целостности между каталогом и реестром нет. Провайдера с моделями пакет не удаляет, но удаление провайдера и добавление модели в одну секунду могут разойтись. Модель без провайдера — состояние, которое продукт показывает: `unavailableReason` `provider_missing` в «Мой доступ», отказ старта и сбой агента с той же причиной, а не сырая ошибка
- Ключ читается из базы на каждом вызове; кэша клиентов нет, потому что он не видит ключ, сменённый на другом экземпляре
- Контроллеру, которому нужны факты обеих сторон, нужны оба модуля: `GET /api/access/models` переезжает в `AccessAdminModule`

### Consequences for future code

- Новый вид провайдера — новый адаптер в `agents`; таблицы `access_*` он не трогает
- Новое правило каталога, которому нужен факт о провайдере, получает его входом от контроллера, а не чтением `agent_model_providers`
- Кэш подключений возможен только вместе со способом видеть смену ключа на другом экземпляре

## Implementation Guidance

- `agent_model_providers` читает и пишет только пакет `agents`; `apps/api` зовёт `Agents.providers`
- Пишущая операция возвращает «было» и «стало», где ключ — `changed`, а не значение ([write-only-secret.md](../code-system/patterns/write-only-secret.md))
- Ключ, прочитанный или принятый, сразу попадает в память секретов логгера (`rememberSecret`)
- Канонический вид таблицы и транзакции — [repository-over-transaction.md](../code-system/patterns/repository-over-transaction.md)
