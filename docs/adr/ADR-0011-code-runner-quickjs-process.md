# ADR-0011 Недоверенный код исполняет QuickJS в отдельном процессе Node 26 с моделью разрешений, а правила держит процесс API

## Status

Proposed (2026-11-14). Ждёт решения владельца.

## Decision

Агенты получают инструмент `run_code`: модель пишет скрипт на JavaScript, и платформа исполняет его на своём сервере. Решено исполнять скрипт в QuickJS, собранном в WASM, внутри отдельного процесса Node 26: пакет `packages/code-runner` запускает такой процесс на каждый запуск с моделью разрешений Node, пустым окружением и единственным разрешением — читать свой код и QuickJS. Процесс исполнителя ничего не решает сам. По мосту — каналу stdin и stdout, где каждое сообщение (кадр) — длина, затем JSON, — он только присылает просьбы вызвать инструмент или прочитать результат, а процесс API проверяет каждую просьбу той же проверкой, что вызов агента, пишет аудит и сам ходит к MCP-серверу. Скрипт в каждом запуске видит одни и те же функции — `callTool`, `readResult`, `console` — и зовёт инструменты под именами из списка инструментов модели. Решение исключает исполнение недоверенного кода в процессе платформы, в его потоках и вне нашего сервера, а весь репозиторий переходит на Node 26.

### Decision Details

| Item | Content |
|------|---------|
| **Why now** | `run_code` — первый недоверенный код на сервере платформы; под мост и API скрипта сразу пишутся правило выбора кода для модели и набор тестов на побег |
| **Known unknowns** | Замечает ли QuickJS срок внутри длинной встроенной операции на огромных данных; сколько памяти WASM займёт взломанный скрипт до своего предела; закрыты ли в вендоренном коммите QuickJS ошибки памяти, опубликованные в конце 2025 года, — сверки не было, и минимальная исправленная версия Node 26.x не закреплена |
| **Kill criteria** | QuickJS не укладывается в NFR-01 или NFR-02 на реальных данных — движок меняется внутри процесса исполнителя; побег из V8 или WASM становится реальной угрозой — за `CodeRunner.run` встаёт контейнер |

## Context

Скрипт нужен, чтобы модель считала по полным данным в мегабайты и не тянула их в свой контекст. Скрипт — недоверенный ввод: самая вероятная атака — внедрённый в данные текст, который заставляет модель написать скрипт, бьющий в ошибку памяти QuickJS. Захватив процесс исполнителя, такой скрипт может слать по мосту любые сообщения.

Варианты должны были выполнить четыре условия:

- данные сотрудников не уходят с нашего сервера ([prd.md](../features/code-execution/prd.md), Constraints и Won't Have);
- изоляция работает на Windows разработчика и на Ubuntu в CI, а Docker в проекте есть только для Postgres;
- преград две: взлом песочницы языка не даёт доступа к памяти процесса платформы, секретам и базе (NFR-05);
- скорость: пустой скрипт и сведение 5 МБ укладываются в NFR-02 и NFR-01.

Модель разрешений Node (режим `--permission`) закрывает процессу файлы, дочерние процессы, потоки и нативные модули. Сеть она закрывает только с Node 25: `--allow-net` появился в v25.0.0, а репозиторий был на Node 24. На Node 24.11.0 процесс под `--permission` открывает TCP и разрешает имена DNS, то есть на старой версии вторая преграда пропадает молча.

Спайк проверил это на Node 26.13.1 и `quickjs-emscripten` 0.32.0 (сборка bellard, вариант `release-sync`) под Windows 11 и под Linux (`node:26-bookworm`). `@jitl/quickjs-wasmfile-release-sync` 0.32.0 несёт QuickJS коммита 2025-09-13+f1139494 ([bellard/quickjs f1139494](https://github.com/bellard/quickjs/commit/f1139494d18a2053630c5ed3384a42bb70db3c53)); по этому коммиту ревью сверяют движок с известными уязвимостями. С пустым `env` процесс получил отказ на каждом пути набора UC-E4: сеть, запись файлов, процессы, потоки, аддоны, инспектор, WASI. QuickJS работает под `--permission` без `--allow-wasi`. Пустой скрипт — p95 73 мс (NFR-02), 21 000 записей лога на 6,38 МБ сгруппированы за 205–228 мс (NFR-01). Обе цели выполнены с запасом больше чем на порядок.

Спайк нашёл и две вещи, которые модель разрешений не закрывает сама:

- путь чтения она проверяет по написанию, а не по реальному пути, поэтому ссылка внутри разрешённого каталога ведёт куда угодно: через junction и symlink спайк прочитал файл `.env` вне разрешённых каталогов;
- `process._debugProcess` не проверяет ни одна область разрешений, и процесс исполнителя открыл им инспектор процесса API. Путь закрывает флаг `--disable-sigusr1` у процесса API или удаление `_debugProcess` в процессе исполнителя — каждое по отдельности.

**Почему это архитектурное решение.**

1. **Дорого откатить.** Под мост и API скрипта пишутся правило выбора кода в инструкциях модели и набор тестов на побег по слоям. Весь репозиторий переходит на Node 26, а процесс API стартует с `--disable-sigusr1` во всех формах запуска, кроме отладочной. Смена движка или места исполнения переписывает тесты на побег и меняет то, что модель знает о скрипте.
2. **Связывает за пределами фичи.** Любое исполнение недоверенного кода на сервере, например серверный код `app-builder`, идёт через этот исполнитель. Слой «Исполнитель кода» записан в [code system](../code-system/README.md).
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Только отдельный процесс с моделью разрешений даёт вторую преграду без контейнера и одинаково на Windows и Linux, а QuickJS внутри него — первую: в языке нет окружающих возможностей — ни файлов, ни сети, ни таймеров, только функции, которые платформа положила в скрипт. Правила держит процесс API, потому что процесс исполнителя считается захваченным: правило, которое живёт только в нём, не правило. Поэтому просьбы проходят ту же проверку `ToolRunner.check`, что вызов агента, и правила остаются в одном месте. Скорость QuickJS спайк измерил с запасом, поэтому более быстрый движок не нужен.

### Options Considered

Где и чем исполнять скрипт.

1. **`isolated-vm` в процессе API**
   - Pros: Изолят V8 с JIT — самый быстрый движок, и процесс на запуск не стартует.
   - Cons: Преграда одна: побег из изолята попадает в процесс платформы с секретами, пулом базы и памятью всех сотрудников (NFR-05).

2. **`isolated-vm` 7.x в процессе исполнителя (запасной)**
   - Pros: Быстрее QuickJS, поддерживает Node 26 и стоит за той же второй преградой.
   - Cons: Не понадобился: QuickJS уложился в NFR-01 и NFR-02 с запасом. Остаётся записанной заменой движка, если замеры на реальных данных провалятся.

3. **`worker_threads`**
   - Pros: Встроен в Node и стартует дешевле процесса.
   - Cons: Тот же процесс и та же память, то есть преграда одна.

4. **Контейнер на каждый запуск**
   - Pros: Изоляция ОС останавливает даже побег в машинный код.
   - Cons: Docker в проекте есть только для Postgres, а изоляция должна работать на Windows разработчика. Контейнер встанет позже за тем же `CodeRunner.run`.

5. **Внешняя песочница или исполнение кода у провайдера модели**
   - Pros: Изоляцию держит чужая инфраструктура.
   - Cons: Данные сотрудников уходят с нашего сервера (PRD, Won't Have).

6. **Остаться на Node 24**
   - Pros: Не нужен переход всего репозитория на новую версию.
   - Cons: В 24.x модель разрешений не закрывает сеть, и скрипт, вышедший из QuickJS, открыл бы соединение с Postgres, API или интернетом.

7. **QuickJS в WASM в короткоживущем процессе Node 26 с моделью разрешений (выбран)**
   - Pros: Две преграды на Windows и Linux без контейнера; процесс на запуск не оставляет состояния между запусками; движок или контейнер меняются за `CodeRunner.run` так, что агенты этого не замечают.
   - Cons: Весь репозиторий переходит на Node 26 одной версией; каждый запуск стоит старта процесса; побег в машинный код вторая преграда не останавливает (Negative Consequences).

Где держать правила и как скрипт зовёт инструменты.

8. **Свой путь к MCP внутри `run_code`**
   - Pros: Исполнитель кода не трогает `ToolRunner`.
   - Cons: Вторая копия проверок прав, набора и аргументов, которая расходится с первой.

9. **Исполнять просьбы через `runOutside`**
   - Pros: Готовый путь прямого вызова.
   - Cons: Он режет ответ до среза для модели, а скрипту нужен полный ответ.

10. **Параллельные вызовы из скрипта**
    - Pros: Скрипт со многими вызовами кончается быстрее.
    - Cons: Нужен ещё один предел — на вызовы в полёте, — а требования на него нет.

11. **Объект инструментов под сессию в песочнице (`tools.x(...)`)**
    - Pros: Вызов читается как обычная функция.
    - Cons: Второе написание тех же имён, которое надо генерировать внутри песочницы под каждый набор серверов.

12. **Процесс API держит каждое правило, просьбы идут по одной через `ToolRunner.callFromCode`, скрипт зовёт инструмент одной функцией `callTool` под именем из списка модели (выбран)**
    - Pros: Правила в одном месте; захваченный процесс исполнителя не меняет ни владельца, ни набор, ни класс запуска; одна система имён служит списку модели, скрипту и аудиту.
    - Cons: `Promise.all` в скрипте работает, но вызовы идут друг за другом.

## Consequences

### Positive Consequences

- Две преграды (NFR-05): язык без окружающих возможностей и процесс без сети, записи файлов, дочерних процессов, потоков, нативных модулей и секретов
- Каждый вызов из кода проходит ту же проверку прав, что вызов агента, и попадает в аудит до обращения к серверу
- Исполнитель работает на Windows разработчика и в CI без Docker
- Контейнер или другой движок встаёт за `CodeRunner.run` без правок в агентах

### Negative Consequences

- Весь репозиторий — CI, README, `@types/node` во всех пакетах — переходит на Node 26 сразу
- Процесс API стартует с `--disable-sigusr1` в каждой форме запуска, кроме отладочной, и в работниках Vitest; без флага путь к его инспектору держит только подготовка процесса исполнителя
- Разрешение на чтение можно давать только каталогам, где ни одна ссылка не ведёт наружу, поэтому каталог пакета исполнителя с его `node_modules` не разрешается, а пути к QuickJS процесс API вычисляет при старте
- **Принятый риск — побег в машинный код.** Ошибка V8 или WASM, которая даёт машинный код в процессе исполнителя, обходит модель разрешений: та проверяет вызовы API Node, а не системные вызовы, и документация Node называет её ремнём безопасности, а не защитой от злонамеренного кода. Такой код может открыть сокет к локальному Postgres с учётными данными из `infra/docker-compose.yml` или к API с подменой `x-user-id`, прочитать файлы и открыть инспектор процесса API того же пользователя ОС. Риск принят, пока за тем же `CodeRunner.run` не встанет контейнер.

### Neutral Consequences

- В QuickJS сборки bellard нет `Intl`, и это совпадает с Won't Have PRD
- `--max-old-space-size` не считает память WASM: честный скрипт ловит предел QuickJS, а взломанный ограничен только пределом роста памяти WASM, заданным сборкой QuickJS, и сроком запуска

## Implementation Guidance

- Недоверенный код на сервере исполняется только через `CodeRunner.run` пакета `packages/code-runner`; второго исполнителя не появляется
- `code-runner` не знает об агентах и зависит только от `common`; вызывает его только `agents`
- Процесс исполнителя запускается через `spawn` от `process.execPath`, а не `fork`, с `--permission`, пустым `env` и без разрешений сети, записи, процессов, потоков, аддонов и WASI
- `createCodeRunner` отказывает под Node ниже 26, а исполнитель собирается при старте процесса API, поэтому платформа не работает на версии, где модель разрешений оставляет сеть открытой
- Разрешение на чтение получают только абсолютные каталоги, в которых ни одна ссылка не ведёт за разрешённые пути: собранный вход исполнителя (в нём ссылок нет) и записи хранилища pnpm с QuickJS по реальному пути (их ссылки ведут друг в друга). Как именно процесс исполнителя находит QuickJS, описывает дизайн (Contract Definitions, пакет `code-runner`). Каталог, где ссылка может вести наружу, например корень пакета с его `node_modules`, не разрешается никогда; вход исполнителя в тестах подчиняется тому же правилу
- Процесс исполнителя до создания QuickJS удаляет `process._debugProcess`, а процесс API стартует с `--disable-sigusr1`: преграды две, и каждая закрывает путь сама
- Владельца, агента, сессию, набор инструментов, класс запуска и подтверждение процесс API связывает с запуском при старте и не берёт из сообщений моста
- Мост — кадры «длина, затем JSON» с закрытым набором сообщений; длина проверяется до чтения тела, а любое нарушение убивает процесс и заканчивает запуск ошибкой
- Внутри песочницы под сессию ничего не строится: API скрипта одинаково в каждом запуске, а имена инструментов — те, что видит модель
