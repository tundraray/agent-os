# ADR-0010 Форма результата агента может нести ограниченный код процесса из закрытого реестра движка

## Status

Accepted (2026-11-08). Расширяет [ADR-0009](ADR-0009-agent-definitions-as-process-data.md): определение агента по-прежнему называет форму результата по имени, а запись реестра формы может нести пролог, закрытие и принудительный конец. ADR-0009 не правится на месте.

## Decision

Процессу на агентах нужно то, чего модель делать не должна: собрать проверяющему пакет утверждения, поставить статус по его оценке, записать ответ и собрать ответ кодом, когда у корня кончился бюджет. Решено, что запись закрытого реестра форм результата в коде движка может нести три функции процесса: пролог до первого хода, закрытие на вызове `finish` и принудительный конец вместо сбоя по бюджету, сроку, пределу ходов или недоступной модели. У каждой функции есть чистый шаг, который решает; шаг чтения необязателен, шаг записи есть только у закрытия и принудительного конца, и модель, внешнюю систему и постановку задач не вызывает ни один шаг. Конфигурация называет форму только по имени, поэтому процесс остаётся данными.

Сужает два правила Implementation Guidance ADR-0009: код процесса формы из закрытого реестра — допустимое исключение из «не содержит шагов отдельного процесса», а код форм проверяется тестовой формой обвязки через внутреннюю сборку движка, а не процессом из одних данных.

### Decision Details

| Item | Content |
|------|---------|
| **Why now** | `deep-research` v3 строит на формах проверку утверждения, ворота закрытия и ответ кодом ([design-research-flow.md](../features/agent-runtime/design-research-flow.md), KD-2, KD-3); после первых расследований по v3 их статусы, ответы и таблица групп зависят от кода форм |
| **Known unknowns** | Понадобятся ли свои формы следующим процессам на агентах |
| **Kill criteria** | Каждый новый процесс на агентах приносит свои формы с кодом процесса, и реестр форм растёт ради одного процесса за другим |

## Context

ADR-0009 сделал процесс словарём определений агентов, а форма результата в нём была только схемой ответа `finish`. Определение называет инструменты и форму из закрытых реестров движка, а код движка не ветвится по `processId` и не содержит шагов отдельного процесса ([design-agent-core.md](../features/agent-runtime/design-agent-core.md), KD-7).

Процессу `deep-research` v3 этого мало ([design-agent-core.md](../features/agent-runtime/design-agent-core.md), KD-8). Статус утверждения ставит код по ответу проверяющего, а не модель по своему тексту ([ADR-0008](ADR-0008-claim-status-from-verifier-answer-and-universal-atoms.md)). Ответ расследования пишет код, а когда у корня кончился бюджет, ответ из проверенного тоже собирает код. Варианты должны были сохранить три вещи: процесс остаётся данными; каждая запись идёт в охраняемой транзакции runtime и не повторяется после рестарта ([ADR-0001](ADR-0001-durable-runtime-owner.md)); дочерняя работа ставится только вызовом агента, под долями и пределами.

**Почему это архитектурное решение.**

1. **Дорого откатить.** Убрать код форм — значит заплатить трижды. Отпечаток определения включает имя и `version` формы, поэтому смена механизма делает недействительными все таблицы групп, которые им ключуются, и требует новой калибровки. В строке запуска агента появляется хранимая колонка входа пролога. Статусы утверждений и ответы сохранённых расследований v3 записал код, которого после отката не будет, и их уже нельзя воспроизвести.
2. **Связывает за пределами фичи.** Формы `research-flow`, калибровка проверяющего через `Engine.assessAgent`, правила `self-correction` для памяти проверяющего и будущие процессы на агентах строятся на этом контракте.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Код формы сохраняет то, ради чего принят ADR-0009: конфигурация — данные, а поведение — только из закрытого реестра в коде. Исключение из правила «код не содержит шагов отдельного процесса» имеет четыре границы:

- форму называет определение по имени, и любая конфигурация формы агентов может назвать любую форму, если соблюдает её ограничения места, которые загрузка проверяет одинаково для всех форм;
- код формы никогда не читает `processId`;
- код формы подчиняется контракту шагов: решает чистый шаг, а чтение и запись идут в охраняемой транзакции;
- реестр наполняет только сборка движка; пакеты вне движка, в том числе `apps/api`, его не дополняют.

Критерий отказа ADR-0009 звучит так: «Новые процессы раз за разом требуют поведения, которое не выражается определениями, инструментами реестра и пределами, и реестр растёт на один инструмент ради одного процесса». Формы v3 — его первый случай, и он принят намеренно: без кода форм v3 не ставит статус по ответу проверяющего и не отвечает, когда кончился бюджет. Если и следующим процессам понадобятся свои формы, сработает критерий отказа этого ADR, а с ним и ADR-0009.

### Options Considered

1. **Инструмент записи у агента, а потом `finish`**
   - Pros: Форма остаётся только схемой, а запись делает инструмент класса `write`, как заметку памяти.
   - Cons: Каждый результат стоит лишнего хода, а запуск, у которого кончился бюджет, всё равно кончается сбоем без ответа.

2. **Код процесса в потребителе `engine.lifecycle` после сбоя корня**
   - Pros: Ответ кодом собирается в одном месте, без кода у формы.
   - Cons: Потребитель беседы получает сбой задачи корня и показывает «Не удался», хотя ответ есть.

3. **Проверка утверждения отдельной задачей runtime рядом с агентом**
   - Pros: Проверка исполняется как задача v2, без агента и без кода формы.
   - Cons: Появляется второй путь постановки дочерней работы мимо долей и пределов `call_agent`.

4. **Код процесса у формы результата из закрытого реестра движка (выбран)**
   - Pros: Решение кода и результат запуска пишет одна охраняемая транзакция, и после рестарта запись не повторяется; принудительный конец даёт ответ вместо сбоя; чистые шаги проверяющего работают вне расследования с тем же решением, что в нём.
   - Cons: Форма перестаёт быть только схемой; правка кода формы меняет решения без смены конфигурации, поэтому её должна сопровождать новая `version`.

## Consequences

### Positive Consequences

- Статус утверждения, ворота закрытия и ответ пишет код той же записью, что результат запуска агента
- Корень, у которого кончился бюджет, срок или ходы, кончается ответом из проверенного, а не сбоем
- Калибровка гоняет те же чистые шаги проверяющего вне расследования, что работают в нём

### Negative Consequences

- В реестре движка появляются формы, которые сейчас использует один процесс
- Правка кода формы без новой `version` оставляет прежний отпечаток, и таблица групп продолжает действовать для изменённых решений

### Neutral Consequences

- Базовая форма `text` кода процесса не несёт, и процессы без своих форм работают как по ADR-0009

## Implementation Guidance

- Конфигурация называет форму результата только по имени из закрытого реестра; форма вне реестра или не на своём месте — отказ при загрузке
- Реестр форм собирает внутренняя сборка движка; публичная сборка движка параметра форм не принимает, и пакеты вне движка реестр не дополняют
- Код формы не читает `processId` и не зовёт модель, внешнюю систему, постановку задач и функции попытки runtime
- Решает только чистый шаг; он читает лишь свой вход и неизменные данные, которые сборка движка передала форме, а чтение базы и запись идут в одной охраняемой транзакции с проверкой, что расследование активно; под оценкой вне расследования одна привязка — таблица по паре отпечатков — заменяется пометкой «калибруемый»
- Строки шага записи фиксируются той же записью, что отмечает исполнение функции, поэтому повтор после рестарта ничего не пишет второй раз
- Код форм проверяется тестовой формой, которую обвязка движка добавляет в реестр через внутреннюю сборку, а не процессом из одних данных
- Правка кода формы, которая меняет её решения, поднимает `version` формы, а с ней отпечаток определения
