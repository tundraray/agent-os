# ADR-0005 Процесс исследования задаёт только конфигурация-данные `ProcessConfig`

## Status

Superseded by [ADR-0009](ADR-0009-agent-definitions-as-process-data.md)

Расширен ADR-0009 (2026-11-08): вторая форма конфигурации — определения агентов. Форма ролей удалена из кода вместе с процессом v2 (agent-runtime / research-flow, T7.0), и процесс задают только определения агентов.

## Decision

Процесс исследования должен описываться так, чтобы позже его мог составить пользователь, а платформа — хранить и выдавать по правам. Единственное определение процесса — JSON-объект `ProcessConfig` (конфигурация процесса): цель, включённые возможности и их лимиты, источники, промпты и модели ролей, бюджеты окна и формат ответа. Строгая схема проверяет конфигурацию до старта любого расследования и отклоняет неизвестный ключ. Возможности берутся только из закрытого реестра движка, поэтому исполняемому коду в конфигурации негде поместиться. Решение исключает процесс как модуль TypeScript, процесс как Mastra workflow и язык выражений для переходов. Поставляемая конфигурация глубокого исследования — такие же данные и проходит ту же проверку.

### Decision Details

| Item | Content |
|------|---------|
| **Why now** | Первая поставляемая конфигурация задаёт формат; после того как `workflow-templates` начнёт хранить шаблоны пользователей, смена формата — это миграция хранимых данных |
| **Known unknowns** | Как хранимые шаблоны переносятся на новую версию схемы и какие версии принимает движок — решает `workflow-templates`. Как права пользователя сужают источники конфигурации — решает `access-control` |
| **Kill criteria** | Шаблоны пользователей раз за разом требуют поведения, которое не выражается возможностями, промптами и лимитами, и реестр растёт на одну возможность ради одного шаблона |

## Context

Требование PRD (FR-12) запрещает зашивать процесс в движок: всё, что относится к процессу, читается из одной конфигурации, а глубокое исследование поставляется единственной такой конфигурацией. Формат — задел для шаблонов процессов пользователей. Редактор, хранение и выбор шаблона при запуске принадлежат будущей фиче `workflow-templates`, а права на источники — фиче `access-control` ([prd.md](../features/deep-research/prd.md), Won't Have). PRD называет и риск этого задела: формат, удобный для одного процесса, может не подойти пользовательским шаблонам (Risks).

Движок — пакет `@agent-os/engine`, который владеет реестром возможностей, контроллером и конфигурацией процесса ([ADR-0004](ADR-0004-agent-framework-packages.md)). Контроллер — долгоживущая задача runtime: на каждом шаге он выбирает одно решение из закрытого набора, а код проверяет решение и ставит задачи ([design-engine.md](../features/deep-research/design-engine.md), KD-2). Durable-владелец исполнения, чьё состояние переживает перезапуск, один — runtime, и workflow приложения на экземпляре Mastra не регистрируются ([ADR-0001](ADR-0001-durable-runtime-owner.md)).

Решение связывает не только `deep-research`: ему подчиняются `workflow-templates`, `access-control` и каждый следующий процесс исследования.

## Rationale

Пользовательский шаблон хранится, проверяется и выдаётся по правам как запись, а не как код, поэтому формат процесса обязан быть данными с самого первого процесса. Строгая схема и закрытый реестр проверяют это при загрузке. Конфигурацию с возможностью вне реестра, с неизвестным ключом или с полем шаблона промпта вне закрытого списка загрузка отклоняет с путём ошибки (AC-12.2). Переходы между шагами уже выбирает контроллер из допустимых решений, так что выражать их в конфигурации не нужно: конфигурация только включает возможности и ставит лимиты.

### Options Considered

1. **Процесс как TS-модуль с функциями шагов**
   - Pros: Шаги процесса — обычный код пакета, и любую логику перехода можно написать прямо в нём.
   - Cons: Пользовательский шаблон (`workflow-templates`) не может быть кодом, поэтому поставляемый процесс и шаблоны жили бы в двух разных форматах.

2. **Процесс как Mastra workflow**
   - Pros: Шаги и их порядок описываются готовым механизмом фреймворка, который уже стоит в проекте.
   - Cons: ADR-0001 запрещает регистрировать workflow приложения на экземпляре Mastra: исполнением владеет только runtime.

3. **Язык выражений для переходов в конфигурации**
   - Pros: Конфигурация остаётся текстом и при этом описывает условные переходы между шагами.
   - Cons: Выражение — исполняемый код внутри данных, то есть ровно то, что FR-12 исключает. Переходы и так выбирает контроллер.

4. **Конфигурация-данные со строгой схемой и закрытым реестром возможностей (выбран)**
   - Pros: Поставляемый процесс и будущие шаблоны имеют один формат и одну проверку (AC-12.3). Вторая конфигурация с другой целью, возможностями и промптами исполняется без изменения кода движка (AC-12.1).
   - Cons: Поведение, которого нет среди возможностей, полей промпта и лимитов, требует изменения кода движка.

## Consequences

### Positive Consequences

- Конфигурация с ошибкой отклоняется при загрузке, до старта расследования, с путём к ошибочному полю (AC-12.2); контракт отказа — в design-engine.md, Contract Definitions
- Решение контроллера, чья возможность не включена в конфигурации, отклоняется так же, как решение вне набора (DC-1)
- Модель любой роли, в том числе всех ролей сразу, меняется правкой конфигурации без изменения кода движка (AC-10.2)

### Negative Consequences

- Новая возможность или новое поле шаблона промпта — это выпуск пакета движка, а не правка конфигурации
- Схема `ProcessConfig` становится контрактом хранимых данных, как только появятся шаблоны пользователей; её изменение потребует переноса хранимых шаблонов, способ которого не выбран

### Neutral Consequences

- Конфигурация глубокого исследования поставляется файлом данных пакета движка
- Расследование хранит замороженную копию конфигурации, с которой стартовало

## Implementation Guidance

- Процесс описывает только `ProcessConfig`; код движка не ветвится по `processId` и не содержит шагов отдельного процесса
- Схема строгая: неизвестный ключ — отказ. Загрузка из файла и создание движка проверяют конфигурацию одной и той же схемой
- Конфигурация ссылается на возможность только по имени из закрытого реестра; новая возможность добавляется в реестр движка вместе с правилом, какие решения контроллера она открывает
- Шаблон промпта подставляет только поля из закрытого списка; условия, выражения и вызовы в шаблоне не допускаются
- Источник и инструмент конфигурации должны быть в allowlist задачи `source.fetch` — списке источников и инструментов, которые runtime разрешает вызывать; права пользователя сужают этот набор, а не расширяют его
- Поставляемые конфигурации проходят ту же проверку, что любые другие; отдельного доверенного пути загрузки нет
- Каждое изменение схемы `ProcessConfig` проверяется второй конфигурацией с другой целью и возможностями, которая исполняется без изменения кода движка (AC-12.1)
