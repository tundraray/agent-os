# ADR-0012 API закрыт сеансом по умолчанию, а владелец данных — UUID сотрудника, который выдаёт сервер

## Status

Accepted (2026-11-15). Связь столбца владельца с сотрудником — по [design-schema.md](../features/data-model/design-schema.md) фичи `data-model`, KD-4 (2026-11-23).

## Decision

API должен знать, какой сотрудник прислал запрос, и не открываться через маршрут, о котором забыли. Решено так. Одна глобальная асинхронная проверка `SessionGuard` стоит на всём API и пропускает без сеанса только маршруты с пометкой `@Public()`. Маршрут с пометкой `@AdminOnly()` она пускает только к сотруднику с правом администратора. Сотрудник — строка `identity_users` с UUID, который сервер создаёт сам, и этот UUID лежит в `req.user.id` и в каждом столбце владельца. Столбец владельца — uuid с внешним ключом на `identity_users`, а работа самой платформы пишется без владельца. Решение заменяет заглушку, которая верила заголовку `x-user-id`, ставилась на каждый контроллер отдельно и по умолчанию считала запрос запросом `dev-user`. Оно исключает идентификатор из данных IdP, владельца-текст без внешнего ключа и служебного сотрудника для работы платформы.

## Context

До фичи `enterprise-access` настоящего входа не было. `SessionGuard` был синхронной заглушкой: в разработке он брал сотрудника из заголовка `x-user-id` или ставил `dev-user`, а в продакшене отказывал всем. Его ставили на каждый контроллер через `@UseGuards`, поэтому новый контроллер был открыт, пока о нём не вспомнили. NFR-03 требует, чтобы без сеанса были открыты только вход и проверка здоровья.

Данные сотрудника — беседы, задачи, сессии агентов, запросы решений, журнал токенов — принадлежат строке владельца. Это шесть текстовых столбцов `owner_id` без внешнего ключа и `runtime_inbox.sender`. Обработчики берут владельца в первой строке (`req.user.id`) и ищут объект вместе с владельцем, так что чужой объект отвечает как отсутствующий.

Варианты должны были выполнить четыре условия:

- один сотрудник — одна учётная запись при входе по паролю и через любого провайдера (AC-04.2);
- идентификатор сотрудника никогда не начинается с `system:`: префикс зарезервирован за служебными владельцами (AC-04.4);
- нижние слои (`runtime`, `agents`) не зависят от слоя приложения ([code system](../code-system/README.md));
- изоляция «чужое = нет» не меняется.

Позже все таблицы и репозитории переехали в одну базу `packages/db` ([ADR-0022](ADR-0022-one-database-and-nestjs-modules.md)), и довод о слоях против внешнего ключа от владельца отпал. Остался вопрос, кто владеет работой самой платформы — задачами эмбеддингов знаний и их строками в журнале расходов ([design-schema.md](../features/data-model/design-schema.md), KD-4).

**Почему это архитектурное решение.**

1. **Дорого откатить.** Значение владельца пишется во все таблицы с данными сотрудника, а смена идентификатора переписывает эти данные во всех таблицах. Каждый маршрут полагается на то, что он закрыт по умолчанию.
2. **Связывает за пределами фичи.** Каждый будущий контроллер, каждый новый столбец владельца и каждая часть `mcp-connect`, `access`, `admin` следуют этому правилу.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Глобальная проверка переворачивает ошибку забывчивости. Забытая пометка `@Public()` даёт отказ, а не открытый маршрут. Серверный UUID не меняется ни при смене почты, ни при входе через другое подключение. Он не берётся из данных IdP, поэтому не может начаться с `system:`, а AC-04.4 держит сам тип столбца. Столбец владельца ссылается на сотрудника внешним ключом, поэтому база не пускает владельца, которого нет. Работа платформы пишется с пустым владельцем: фильтр с id сотрудника её не находит, и в расход сотрудника она не входит. Обработчики и поиск «чужое = нет» не меняются.

### Options Considered

Идентификатор сотрудника.

1. **Почта из IdP**
   - Pros: Читается человеком; сотрудника и так узнают по подтверждённой почте.
   - Cons: Почта меняется, и тогда данные пришлось бы переписывать во всех таблицах. Строка из IdP в `owner_id` могла бы начаться с `system:`.

2. **`sub` из IdP**
   - Pros: Стабилен внутри одного подключения.
   - Cons: У двух подключений одного сотрудника `sub` разный, а AC-04.2 требует одну учётную запись. Это тоже строка из IdP.

3. **UUID, который выдаёт сервер (выбран)**
   - Pros: Не меняется и не зависит от подключения; `system:` в него не помещается.
   - Cons: В данных стоит ничего не говорящий человеку UUID; почта и имя читаются из `identity_users`.

Связь столбцов владельца с сотрудником.

4. **Внешний ключ из `owner_id` на `identity_users`, у работы платформы владельца нет (выбран)**
   - Pros: База сама не пускает владельца, которого нет. Работе платформы не нужен выдуманный владелец.
   - Cons: Тест получает владельца, только создав сотрудника. Пустой владелец — значение, которое ни один фильтр сотрудника не должен передавать.

5. **Текст без внешнего ключа**
   - Pros: Обработчики не меняются, служебный владелец пишется строкой (`'platform'`).
   - Cons: Целостность «владелец существует» держит код, а не база; в данных копятся владельцы без сотрудника.

6. **Внешний ключ и служебный сотрудник для работы платформы**
   - Pros: У каждой строки есть владелец.
   - Cons: Служебный сотрудник появился бы в списках сотрудников, в правах и в проверке активности владельца.

Где стоит проверка.

7. **Проверка на каждом контроллере, как сейчас**
   - Pros: Видно прямо в контроллере, что он закрыт.
   - Cons: Новый контроллер открыт по умолчанию, и NFR-03 нечем держать.

8. **Одна глобальная проверка с пометками `@Public()` и `@AdminOnly()` (выбран)**
   - Pros: Закрыто всё, что не открыто явно; право администратора проверяется в том же месте.
   - Cons: Каждый запрос читает сеанс и сотрудника из базы.

## Consequences

### Positive Consequences

- Новый маршрут любой части закрыт сеансом, пока его не пометили `@Public()`
- Сотрудник остаётся одной учётной записью при смене почты и при входе через OIDC и SAML
- Ни один путь создания сотрудника — локальная учётная запись, JIT, команда оператора — не даёт идентификатор с префиксом `system:`
- Обработчики вида `const ownerId = req.user.id` и поиск «чужое = нет» работают как прежде

### Negative Consequences

- Тест получает владельца, только создав строку `identity_users`: выдуманный id база отвергает
- Поиск задачи с владельцем (`RuntimeTasksRepository.findOwned`) принимает пустого владельца и тогда находит только задачу платформы; так ищут только сообщения между задачами платформы. Вызывающий, который передаст туда пустой владелец задачи вместо id сотрудника, откроет задачи платформы
- Заголовок `x-user-id` удалён, поэтому e2e-тесты и разработчик входят по логину и паролю и несут cookie сеанса
- Каждый запрос стоит одного чтения сеанса и сотрудника из базы

### Consequences for the next parts

- `mcp-connect`: если части нужен маршрут без сеанса, она помечает его `@Public()` и защищает сама
- `access`: таблицы прав ссылаются на `identity_users` и `identity_roles` внешним ключом с каскадом; столбцы владельца заполняются из `req.user.id`; пока `access` не собрана, `MCP_ACCESS_TABLE` ключуется этим UUID
- `admin`: каждый маршрут `/api/admin/...` помечен `@AdminOnly()`, а веб узнаёт сотрудника из `GET /api/auth/me`

## Implementation Guidance

- Маршрут закрыт по умолчанию; `@Public()` ставится только маршруту, который защищает себя сам
- Владелец берётся только из `req.user.id` в первой строке обработчика, никогда из тела, параметров или заголовков
- Пакеты ниже `apps/api` о сеансе не знают и получают строку владельца параметром
- Идентификатор сотрудника выдаёт сервер; значение из IdP никогда не становится идентификатором или значением владельца
- Каждый столбец владельца — uuid с внешним ключом на `identity_users` и каскадом ([ADR-0024](ADR-0024-every-reference-is-a-foreign-key.md)); пустой владелец допустим у задачи движка и строки журнала расходов, где он означает работу платформы, и у агента, где он означает системного агента ([design-agents.md](../features/data-model/design-agents.md), «Таблицы каталога»); объект ищется вместе с владельцем, а чужой отвечает как отсутствующий
- Запрос сотрудника всегда передаёт в фильтр владельца его id, никогда пустое значение
- Канонический вид — паттерн [auth-boundary.md](../code-system/patterns/auth-boundary.md)
