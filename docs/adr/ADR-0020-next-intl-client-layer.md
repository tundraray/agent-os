# ADR-0020 Текст интерфейса веба — библиотека next-intl, только её клиентский слой: без языка в адресе, без плагина, без `getRequestConfig` и без промежуточного слоя next-intl

## Status

Proposed (2026-11-21).

## Decision

Веб показывает интерфейс на английском и русском, и весь его текст нужно брать из каталогов сообщений, а не из кода экранов. Решено: текст интерфейса, даты, числа и суммы идут через библиотеку next-intl, и из неё берётся только клиентский слой. Языковой корень в корневом макете — серверный компонент, который сам выбирает язык, — передаёт язык и сообщения явными свойствами клиентской обёртке над `NextIntlClientProvider`. Компоненты берут текст хуком `useTranslations`, а даты и числа — хуком `useFormatter`.

Решение исключает язык в адресе страницы (i18n-маршрутизацию next-intl и сегмент `[locale]`), плагин `next-intl/plugin`, файл `i18n/request.ts` с `getRequestConfig` и промежуточный слой next-intl в `proxy.ts`.

## Context

Сегодня текст веба записан по-русски прямо в коде: объекты `TEXT` в компонентах, текстовые модули вроде `lib/admin/admin-texts.ts`, строки в JSX. Даты, числа и суммы форматируют объекты `Intl` с `'ru-RU'`, а форму слова при числе считает своя функция в `lib/i18n/plural-ru.ts`. PRD фичи `i18n` требует интерфейс на двух языках, выбор языка в профиле и оформление дат, чисел и сумм по правилам языка ([prd.md](../features/i18n/prd.md), FR-01, FR-02, FR-04).

От библиотеки нужно три вещи:

- сообщения ICU — синтаксис с подстановками, формами множественного числа (`plural`) и выбором по значению (`select`), чтобы фраза с числом или видом записи оставалась целой и верной по роду, а текст и форматы приходили в компоненты хуками;
- форматирование дат и чисел через `Intl` на языке страницы;
- проверка ключей компилятором.

Ограничения задают соседние решения. Язык не входит в адрес страницы, а сервер Next выбирает его сам по cookie `aos_locale` и заголовку `Accept-Language` ([design-web.md](../features/i18n/design-web.md), KD-2). Весь текст сегодня живёт в клиентских компонентах; серверных файлов с текстом два — корневой макет и страница входа, — и их текст переезжает в клиентские компоненты. Приложение работает на `next` 16.4.6 и `react` 19.3.1, собирается Turbopack и включает `cacheComponents: true`. Даты показываются в часовом поясе браузера, а не сервера ([foundations.md](../design-system/foundations.md), «Часовой пояс — браузера»).

**Почему это архитектурное решение.**

1. **Дорого откатить.** Каждый компонент пишется против API библиотеки и формата её каталогов, поэтому замена задевает их все.
2. **Связывает за пределами фичи.** Весь будущий текст интерфейса пишется против этого API и этого формата каталогов.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

next-intl даёт все три вещи: `useTranslations`, `useFormatter` и проверку ключей через объявление типа каталога. Её режим без i18n-маршрутизации — обычный путь для App Router, когда язык не в адресе. Серверный слой библиотеки не нужен: ни один серверный компонент не рисует переведённый текст, а язык выбирает собственный языковой корень.

Проверено: next-intl 4.x объявляет совместимость с `next` 16 и `react` 19. Клиентская точка входа пакета (`index.react-client`) не импортирует `next-intl/config`; его импортируют только плагин и серверные функции (прочитано в пакете 4.14.9). В серверном компоненте тот же импорт `next-intl` разрешается в `index.react-server`, чей `NextIntlClientProvider` читает `next-intl/config` и без плагина падает; поэтому провайдер импортирует только модуль с `'use client'`. Работу связки под Turbopack и `cacheComponents: true` подтверждает первый спайк, до перевода экранов.

### Options Considered

1. **Полная настройка next-intl: плагин `next-intl/plugin` и `getRequestConfig` в `i18n/request.ts`**
   - Pros: Даёт и серверный API перевода.
   - Cons: Плагин оборачивает `next.config` и подставляет вместо `next-intl/config` обязательный файл `i18n/request.ts` — две лишние части ради серверного API, которым приложение не пользуется. Выигрыша под `cacheComponents` нет: серверные функции читают заголовки запроса, поэтому язык всё равно выбирался бы при запросе внутри `<Suspense>`.

2. **Голый `use-intl`**
   - Pros: То же ядро и те же хуки, что у next-intl.
   - Cons: Нет серверного слоя. next-intl позволяет добавить его позже, не меняя хуков и каталогов; с `use-intl` для этого пришлось бы подключать вторую библиотеку.

3. **i18next**
   - Pros: Покрывает перевод, формы множественного числа и форматирование.
   - Cons: Свой формат сообщений: формы множественного числа задаются суффиксами ключей, а ICU доступен только через дополнительный плагин.

4. **Lingui**
   - Pros: Сообщения ICU.
   - Cons: Сообщения пишутся в коде макросами и собираются в каталоги отдельным шагом CLI. Пропущенный перевод ловит этот шаг, а не `tsc`, и сборке нужен плагин макросов.

5. **Свой контекст React с `Intl.PluralRules`**
   - Pros: Нет новой зависимости.
   - Cons: Повторяет библиотеку без синтаксиса ICU, поэтому фразы с числом и видом снова собирались бы из кусков.

6. **next-intl, только клиентский слой, без языка в адресе (выбран)**
   - Pros: Всё нужное есть без серверного API. Язык и сообщения приходят от своего корня явными свойствами, а часовой пояс браузера задаётся явно.
   - Cons: Серверных функций перевода в приложении нет, поэтому переведённый текст рисуют только клиентские компоненты. Работа под Turbopack и `cacheComponents` до спайка остаётся предположением.

## Consequences

### Positive Consequences

- Текст, форматы дат и чисел и формы слова при числе идут через одну библиотеку; `plural-ru.ts` и модульные объекты `Intl` с `'ru-RU'` удаляются
- Английский каталог задаёт тип сообщений, поэтому пропущенный ключ русского каталога отвергает `tsc`
- Язык решает одно место — языковой корень; библиотека язык не выбирает и в адрес его не пишет
- `proxy.ts` по-прежнему ставит только cookie DSN: промежуточного слоя next-intl в нём нет

### Negative Consequences

- Текст двух серверных файлов — корневого макета и страницы входа — переезжает в клиентские компоненты
- Каждая загрузка документа несёт сообщения одного языка целиком ([design-web.md](../features/i18n/design-web.md), Risks and Mitigation, «Вес каталога»)
- До первого спайка работа связки под Turbopack и `cacheComponents` остаётся предположением

### Consequences for future code

- Новый текст интерфейса — сообщение в каталогах `en` и `ru` и хук `useTranslations` в клиентском компоненте ([interface-text.md](../code-system/patterns/interface-text.md))
- Серверному компоненту, которому понадобится переведённый текст, нужен серверный слой next-intl с плагином и `getRequestConfig`; это новое решение вместо этого ADR
- Язык в адресе страницы — тоже новое решение: i18n-маршрутизации нет

## Implementation Guidance

- `NextIntlClientProvider` рисует клиентская обёртка: язык и сообщения она получает явными свойствами от языкового корня, а часовой пояс браузера и общие форматы задаёт сама; приложение не импортирует серверные функции next-intl
- `NextIntlClientProvider` импортирует только модуль с `'use client'`; серверный языковой корень из `next-intl` не импортирует ничего
- Ошибки next-intl пишутся через логгер `lib/logger.ts`
- Фраза с числом, именем или видом — одно сообщение ICU с `plural` и `select`, а не склейка кусков
- Сторы и службы вне React отдают ключ сообщения со значениями, а переводит компонент, который его показывает ([interface-text.md](../code-system/patterns/interface-text.md))
