# ADR-0009 Агентов процесса задают данные: определения агентов в `ProcessConfig` с закрытым реестром инструментов

## Status

Accepted (2026-11-08). Расширяет [ADR-0005](ADR-0005-process-config-data-only.md): ADR-0005 действует для конфигураций формы ролей, а когда процесс `deep-research` v2 удалят, он станет «заменён ADR-0009». ADR-0005 не правится на месте: принятый ADR не редактируется, изменённое решение записывает новый.

## Decision

Стадии расследования становятся агентами, и описание процесса должно сказать, какие агенты в нём работают, что каждый умеет и кого может вызвать. Процесс по-прежнему задаёт только конфигурация-данные `ProcessConfig` со строгой схемой. У неё появляется вторая форма — форма агентов: словарь определений агентов, имя корневого агента и пределы дерева. Определение называет модель, усилие, шаблон промпта, инструменты из закрытого реестра движка, имена агентов, которых можно вызвать, форму результата и пределы запуска. Решение исключает агентов как модули TypeScript и как агентов Mastra, которых описывает и исполняет фреймворк.

### Decision Details

| Item | Content |
|------|---------|
| **Why now** | Первый процесс на агентах (`deep-research` v3) и пробный процесс `agent-core` задают формат; после первых расследований по нему замороженные копии становятся хранимыми данными |
| **Known unknowns** | Хватит ли закрытого реестра инструментов шаблонам пользователей `workflow-templates`; как права сотрудника сужают источники определения — решает `access-control` |
| **Kill criteria** | Новые процессы раз за разом требуют поведения, которое не выражается определениями, инструментами реестра и пределами, и реестр растёт на один инструмент ради одного процесса |

## Context

Сейчас конфигурация описывает процесс ролями: ровно пять ролей с моделью и промптом, закрытый список возможностей и лимиты шагов controller. Переходы между шагами выбирает controller из закрытого набора решений, и каждое новое поведение — новое решение в коде ([design-agent-core.md](../features/agent-runtime/design-agent-core.md), Snapshot). Фича `agent-runtime` делает стадии агентами: агент работает ходами, просит инструменты и вызывает других агентов, а код исполняет вызовы, проверяет права, пределы и бюджет ([prd.md](../features/agent-runtime/prd.md), FR-01, FR-13).

Варианты должны были сохранить три вещи. Процесс остаётся записью, которую позже сохранит и выдаст по правам фича `workflow-templates`, поэтому исполняемого кода в нём нет. Замороженные копии сохранённых расследований v2 разбираются, как раньше (FR-13, FR-14). Исполнением владеет только runtime ([ADR-0001](ADR-0001-durable-runtime-owner.md)).

**Почему это архитектурное решение.**

1. **Дорого откатить.** Каждое расследование хранит замороженную копию конфигурации, с которой стартовало, а `workflow-templates` будет хранить шаблоны пользователей. После первых расследований по форме агентов смена формата — перенос хранимых данных.
2. **Связывает за пределами фичи.** На форме агентов строятся `research-flow`, каталог источников `source-planning` (инструмент агента плана), правила `self-correction` (память определения агента), будущий перевод чат-агента и `workflow-templates`.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Форма агентов сохраняет то, ради чего был принят ADR-0005: процесс — данные, которые строгая схема проверяет до старта, а возможности — только из закрытого реестра в коде. Меняется предмет реестра: вместо возможностей, которые открывают решения controller, — инструменты с классом эффекта, а вместо фиксированного набора ролей — определения агентов с правилом, кого агент может вызвать. Вторая форма рядом с первой, а не новая схема на месте старой, оставляет v2 и замороженные копии нетронутыми, пока v3 не докажет, что она не хуже.

### Options Considered

1. **Заменить ADR-0005 целиком новым ADR и одной новой схемой**
   - Pros: Одна схема конфигурации в движке.
   - Cons: Расследования v2 и их замороженные копии перестали бы разбираться, а v2 по требованию PRD поставляется и остаётся версией по умолчанию до сравнения (FR-14, FR-19).

2. **Агенты как модули TypeScript с описанием в коде**
   - Pros: Любое поведение агента выражается кодом без расширения реестра.
   - Cons: Пользовательский шаблон не может быть кодом, поэтому поставляемые агенты и шаблоны жили бы в двух форматах, — тот же довод, по которому ADR-0005 отверг процесс как модуль.

3. **Агенты Mastra с инструментами и субагентами, описанные конфигурацией фреймворка**
   - Pros: Цикл ходов, исполнение инструментов и субагенты уже готовы во фреймворке.
   - Cons: Работа субагента идёт внутри одного вызова вне задач runtime: без резерва перед каждым запросом, без отмены по расследованию и без восстановления, что запрещает ADR-0001.

4. **Вторая форма `ProcessConfig` — определения агентов с закрытым реестром инструментов (выбран)**
   - Pros: Процесс остаётся данными одной проверки; v2 и сохранённые расследования разбираются прежней схемой; второй процесс из одних данных исполняется без изменения кода движка.
   - Cons: В движке две схемы конфигурации, пока поставляется v2; новый инструмент — выпуск движка, а не правка конфигурации.

## Consequences

### Positive Consequences

- Новое поведение стадии — «копни глубже», «перепроверь до сдачи» — задаётся определением агента и его инструментами, без нового кода цикла
- Конфигурация с инструментом вне реестра, вызовом несуществующего агента или неизвестным ключом отклоняется при загрузке, до старта расследования
- Отпечаток определения считается из данных определения, поэтому калибровка и самопроверка узнают изменённого агента без отдельного поля

### Negative Consequences

- Пока поставляется v2, загрузка выбирает одну из двух схем, а код, который читает роли, получает только конфигурации формы ролей
- Схема формы агентов становится контрактом хранимых данных; способ переноса хранимых шаблонов на её новые версии по-прежнему решает `workflow-templates`

### Neutral Consequences

- Пробный процесс из одних данных живёт в тестовой обвязке движка и не поставляется
- Расследование по-прежнему хранит замороженную копию конфигурации, с которой стартовало, в любой из двух форм

## Implementation Guidance

- Процесс описывает только `ProcessConfig`; код движка не ветвится по `processId` и не содержит шагов отдельного процесса
- Загрузка выбирает форму по наличию ключа `agents` и проверяет каждую форму строгой схемой: неизвестный ключ — отказ
- Определение ссылается на инструмент только по имени из закрытого реестра движка; новый инструмент добавляется в реестр вместе с классом эффекта
- Вызываемые агенты, корневой агент и источники определения проверяются при загрузке на существование в той же конфигурации
- Шаблон промпта определения подставляет только поля из закрытого списка; условия, выражения и вызовы в шаблоне не допускаются
- Источник определения должен быть в allowlist задачи `source.fetch`; права пользователя и вызов агента сужают набор источников запуска, а не расширяют его
- Каждое изменение схемы формы агентов проверяется вторым процессом из одних данных, который исполняется без изменения кода движка
- Поставляемые конфигурации проходят ту же проверку, что любые другие
