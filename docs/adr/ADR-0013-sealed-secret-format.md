# ADR-0013 Каждый секрет в базе запечатан `SecretBox`: AES-256-GCM, номер ключа в значении, назначение в AAD; неверный ключ останавливает старт

## Status

Proposed (2026-11-15). Ждёт решения владельца.

## Decision

Платформа начинает хранить в базе секреты, которые дают доступ к чужим системам. Это секрет клиента IdP, а в части `mcp-connect` — общие учётные записи MCP-серверов и токены сотрудников. Решено, что каждый такой секрет запечатывает `SecretBox` из `packages/common` ключом из `SECRETS_KEY`. Значение — строка из версии формата, номера ключа, IV, шифротекста AES-256-GCM и тега. Назначение значения входит в AAD, поэтому значение не расшифруется в чужой строке. Значение, которое сервер только сверяет, хранится SHA-256 хешем, а не шифротекстом. С неверным ключом сервер не стартует, потерянный ключ заменяет команда `secrets:reset`, а ротации ключа в PoC нет. Решение исключает шифрование в Postgres и внешний сервис ключей.

## Context

До фичи `enterprise-access` ничего не хранило и не шифровало секрет в базе: понятия номера ключа и ротации не было. NFR-01 требует, чтобы секреты подключений входа, токен SCIM, общие учётные записи MCP-серверов и токены сотрудников лежали в базе только зашифрованными. NFR-02 требует, чтобы ни секрет, ни токен не попал в логи, аудит, ответы сервера и историю агентов. Ключ шифрования секретов — одно из немногих значений, которые PRD разрешает фиче добавить в окружение (PRD, Constraints). Пакеты не читают окружение ([ADR-0004](ADR-0004-agent-framework-packages.md)).

Отдельный вопрос — что делать, когда ключ потерян или задан неверно. Секреты подключений входа без ключа не расшифровать, а без подключения войти не может никто, включая администратора.

**Почему это архитектурное решение.**

1. **Дорого откатить.** Формат — сохранённые данные: смена формата или способа шифрования перешифровывает каждую строку с секретом во всех частях.
2. **Связывает за пределами фичи.** Части `mcp-connect` и любой будущий код, который хранит секрет чужой системы, пишут в этом формате.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

`SecretBox` работает на `node:crypto` внутри процесса API, поэтому ключ не выходит за его пределы и не нужна внешняя система. GCM проверяет целостность, а назначение в AAD не даёт переставить шифротекст из одной строки в другую. Номер ключа в каждом значении позволит позже добавить ротацию, не меняя строк. Отказ стартовать с неверным ключом и команда `secrets:reset` дают явный путь восстановления: после стирания первое подключение возвращает bootstrap (FR-09), а администратор вводит секреты заново.

### Options Considered

Как шифровать.

1. **`pgcrypto` в Postgres**
   - Pros: Шифрует сама база, кода шифрования в приложении нет.
   - Cons: Ключ уходит в каждый SQL-запрос и может попасть в лог Postgres.

2. **KMS или Vault**
   - Pros: Ключ хранит и вращает отдельный сервис.
   - Cons: Для одного развёртывания PoC это внешняя система, которой у проекта нет.

3. **`SecretBox` в `packages/common`: AES-256-GCM, номер ключа в значении, назначение в AAD (выбран)**
   - Pros: Ключ остаётся в процессе API; один формат для всех частей; ротацию можно добавить позже, не меняя строк.
   - Cons: Ключ живёт в окружении сервера, и его сохранность — забота оператора.

Что делать с неверным ключом.

4. **Стартовать с неверным ключом**
   - Pros: Сервер поднимается всегда.
   - Cons: Ни одно подключение не расшифровывается, и войти не может никто, включая администратора.

5. **Не стартовать и стереть секреты командой `secrets:reset` (выбран)**
   - Pros: Причина видна в логе сразу, с обоими номерами ключа; путь восстановления один и явный.
   - Cons: Потеря ключа стирает все запечатанные секреты, и их вводят заново.

## Consequences

### Positive Consequences

- В базе нет ни одного секрета в открытом виде (NFR-01)
- Запечатанное значение нельзя расшифровать в строке с другим назначением
- Неверный ключ обнаруживается при старте, а не при первом входе
- Токен SCIM хранится хешем: прочитать его нельзя даже с ключом, и потеря ключа его не касается

### Negative Consequences

- Потерянный ключ — потерянные секреты: оператор запускает `secrets:reset`, подключения входа выключаются, администратор вводит секреты заново
- Ротации в PoC нет: сменить ключ сегодня можно только через `secrets:reset`
- `SECRETS_KEY` обязателен: без него или с неверной длиной сервер не стартует

### Consequences for the next parts

- `mcp-connect` запечатывает в этом формате общие учётные записи MCP-серверов и токены сотрудников, каждое значение со своим назначением
- Часть, которая добавляет столбец с запечатанным значением, добавляет его в стирание `secrets:reset` и описывает в своём дизайне, что становится с её объектами без секрета
- Ответ API о секрете говорит только, задан ли он: секрет можно заменить, но нельзя прочитать

## Implementation Guidance

- Секрет чужой системы хранится только запечатанным `SecretBox`; второго способа шифрования не появляется
- Значение, которое сервер только сверяет, хранится SHA-256 хешем
- `SecretBox` приходит в пакеты параметром функции сборки; окружение читает только `apps/api`
- Секрет открывается там, где нужен для вызова, и нигде не сохраняется открытым; значение не передаётся ни в лог, ни в текст ошибки
- `SECRETS_KEY` входит в список значений, которые маскирует логгер
- Канонический вид — паттерн [sealed-secret.md](../code-system/patterns/sealed-secret.md)
