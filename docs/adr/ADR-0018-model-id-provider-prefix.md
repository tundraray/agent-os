# ADR-0018 id модели — строка `<провайдер>/<имя у провайдера>`, и провайдера называет только её первая часть до первой косой черты

## Status

Accepted (2026-11-20).

## Decision

Платформа теперь зовёт модели нескольких провайдеров, и каждый вызов должен знать, к какому провайдеру идти. Решено: id модели — одна строка `<провайдер>/<имя у провайдера>`. Провайдер — всё до первой косой черты, имя у провайдера — всё после неё, и в имени косая черта допустима: у vLLM модель называется `Qwen/Qwen3-32B`, её id — `local/Qwen/Qwen3-32B`. Провайдер не хранится отдельно ни в одной таблице: его достаёт из id одна функция `modelProvider` в пакете `contracts`, и поле `provider` в ответах API выводится ею же.

Эта строка — контракт между пакетами. Её хранят каталог моделей `access_models`, права и квоты на модель, записи библиотеки и снимки запусков, строки журнала затрат `runtime_model_calls`. Имя провайдера — первичный ключ строки реестра `agent_model_providers` ([ADR-0019](ADR-0019-model-provider-registry-in-agents.md)), и оно не меняется. Id `anthropic/…`, которые уже лежат в данных, остаются верными: когда администратор заводит провайдера `anthropic`, права, квоты и записи на них работают без правок и без миграции (AC-05.4).

Решение исключает запрет косой черты в имени у провайдера, столбец провайдера рядом с голым именем модели и непрозрачный id каталога.

## Context

Сегодня каждый вызов модели идёт в Anthropic. Id моделей уже имеют вид `anthropic/…`, а схема id `ModelIdSchema` в `contracts`, конфиг, веб, сиды и тесты проверяют этот префикс. Фича `model-providers` добавляет провайдеров Gemini и OpenAI-совместимых, и форму id `<провайдер>/<имя>` задаёт её PRD ([prd.md](../features/model-providers/prd.md), FR-05). Имя провайдера — строчные латинские буквы, цифры и дефис, до 32 символов (design-core, FR-01), поэтому косой черты в нём не бывает, и разрез по первой косой черте однозначен.

**Почему это архитектурное решение.**

1. **Дорого откатить.** Id лежит в каталоге, правах, квотах, записях, снимках и журнале. Другая форма — это миграция всех этих данных и правка каждого, кто их читает.
2. **Связывает за пределами фичи.** Каждый новый провайдер, вид провайдера и потребитель модели — служба эмбеддингов, самообучение — называет модель этой строкой и узнаёт провайдера через `modelProvider`.
3. **Были реальные варианты.** Они сравнены ниже.

## Rationale

Форма, которую задаёт PRD, совпадает с id, уже записанными в данных, поэтому ни одна запись не мигрирует. Провайдер известен из самого id: служба вызовов читает строку провайдера по первой части id и не спрашивает каталог. Значение провайдера живёт в одном месте — в id, и два поля не могут разойтись.

### Options Considered

1. **Запрет косой черты в имени у провайдера, как сегодня в `ModelIdSchema`**
   - Pros: id делится на две части одним очевидным способом.
   - Cons: Модель, чьё имя у провайдера содержит косую черту, как `Qwen/Qwen3-32B` у vLLM, нельзя добавить в каталог.

2. **Столбец провайдера рядом с голым именем модели**
   - Pros: Провайдер виден отдельным полем.
   - Cons: Модель называлась бы парой полей в каталоге, правах, квотах, записях, снимках и журнале. Сохранённые id `anthropic/…` пришлось бы переписать (против AC-05.4). Тот же провайдер хранился бы вторым местом рядом с id (KD-4).

3. **Непрозрачный id каталога**
   - Pros: Ссылки не зависят от имён провайдера и модели.
   - Cons: Права, квоты, записи и журнал ссылались бы на номер строки, и сохранённые id `anthropic/…` пришлось бы перевести на номера (против AC-05.4). Форма id в PRD — `<провайдер>/<имя>`.

4. **Одна строка `<провайдер>/<имя у провайдера>`, разрез по первой косой черте (выбран)**
   - Pros: Данные не мигрируют. Провайдер известен из id без чтения каталога. Значение провайдера хранится один раз.
   - Cons: Провайдера нельзя переименовать. Код, который режет id сам, может ошибиться на имени с косой чертой.

## Consequences

### Positive Consequences

- Права, квоты, записи и журнал на `anthropic/…` работают без миграции (AC-05.4)
- Служба вызовов и проверка готовности находят провайдера по id модели, без чтения каталога

### Negative Consequences

- Провайдера нельзя переименовать: его имя — первичный ключ реестра и часть каждого сохранённого id. Новое имя — это новый провайдер и новые модели в каталоге
- Имя у провайдера может содержать косую черту, поэтому id режется только по первой косой черте; разбор по последней черте или подсчёт частей даёт неверного провайдера
- Все проверки префикса `anthropic/` удаляются из схемы, конфига, веба, сидов и тестов

### Consequences for future code

- Провайдера модели берут только через `modelProvider`; собственный разбор id не пишут
- Новый вид модели, как модели эмбеддингов, получает id той же формы и живёт в том же каталоге; назначение модели — поле каталога, а не часть id

## Implementation Guidance

- Форму id проверяет `ModelIdSchema` в `contracts`, провайдера достаёт `modelProvider` там же
- Id хранится текстом во всех таблицах; на реестр провайдеров он не ссылается внешним ключом ([ADR-0019](ADR-0019-model-provider-registry-in-agents.md))
- Правило имени провайдера (без косой черты) держит схема имени провайдера в `contracts`
