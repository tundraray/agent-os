# Обработчик шага

## Problem

Работа длится дольше одного вызова модели или инструмента, должна пережить рестарт сервера и реагировать на прерывание. Признак: цикл «вызвать модель — исполнить инструменты — подождать» или любая фоновая работа с состоянием.

## Shape

- **Задача** в runtime — единица работы с типом, владельцем, родителем и статусом. Работа идёт **шагами**: воркер захватывает один шаг, исполняет его и фиксирует итог одной транзакцией. Шаги исполняет один процесс ([ADR-0023](../../adr/ADR-0023-live-task-objects-one-stepping-process.md)).
- **Тип задачи** регистрируется в `onModuleInit` своего модуля одним из двух способов. `HandlerRegistry.register` — обработчик без состояния (`TaskHandler`): один на все задачи типа, между шагами ничего не держит. `HandlerRegistry.registerLive` — живой тип (`LiveTaskType`): у каждой задачи свой объект (`LiveTask`), и runtime держит его в памяти между шагами.
- **Шаг** получает контекст (вход, сообщения очереди, решённый запрос, сигнал прерывания), делает внешнюю работу вне транзакции и возвращает итог шага. Свои записи он кладёт в функцию `commit(effects)` итога: runtime зовёт её в транзакции итога, и репозитории, которые она зовёт, сами входят в эту транзакцию. Через `effects` шаг создаёт детей, открывает трекер, шлёт сообщения, пишет события и передаёт runtime объект ребёнка (`adopt`).
- **Итог шага** — продолжить, ждать сообщений, ждать решения человека, завершиться или упасть. Runtime фиксирует записи обработчика, доставку сообщений, новый статус и события вместе.
- **Живой объект — кэш над базой.** Источник правды — база. Шаг состояние объекта только читает; объект меняется в `committed`, который runtime зовёт после успешного коммита. При любом другом конце шага (исключение, обрыв, предел шагов, сбой записи), после 15 минут простоя и сверх 500 объектов runtime объект отпускает (`dispose`). Задаче без объекта новый строит `restore` её типа из базы; при старте процесса runtime заранее восстанавливает объекты задач в `queued` и `running`. То, от чего зависят права сотрудника, объект не хранит и читает на каждом шаге.
- **Объект нового ребёнка** строит тот, кто создаёт задачу, в той же транзакции, и отдаёт runtime: шаг — через `effects.adopt`, операция вне шага — через `LiveTasks.adopt` после коммита. Первый шаг ребёнка идёт на этом объекте без `restore`.
- **Ожидание своих детей** — коммит шага открывает трекер с дочерними задачами и кончается итогом «ждать»: задача ждёт задач, и runtime будит её одним сообщением `tasks_finished`, когда закончились все. Ответы детей шаг читает операцией `Trackers.list`, а не из сообщения.
- **Внешнее действие, которое нельзя повторить**, предваряется охраняемой записью намерения внутри шага (`StepContext.guard(work)`). Если шаг потерян, следующая попытка видит признак потери и намерение без результата и решает, что делать, вместо слепого повтора.
- Шаг не держит транзакцию через внешний вызов и проверяет сигнал прерывания перед каждым внешним вызовом. Задачи он меняет только итогом шага и командами сервисов runtime: правила переходов живут в них.
- **Несколько видов работы с общим шагом** — живой тип пишется классом: абстрактный базовый класс держит общий шаг, а каждый вид — его наследник со своим типом задачи. Наследник переопределяет только то, чем отличается, и общий код на вид не ветвится. Класс выбирают один раз, когда создают задачу: её тип и есть выбор. В `agents` это `BaseAgent` и три наследника, а объекты делает `AgentFactory` ([packages/agents.md](../packages/agents.md), Объект агента).

Контракт — [design-runtime.md](../../features/agent-platform/design-runtime.md#contract-definitions).

## Not For

| Looks like | Use instead |
|---|---|
| короткий запрос API, который отвечает сразу | обычный сервис с транзакцией |
| периодическая служебная работа runtime (возврат брошенных задач, доставка событий) | `WorkerLoop` внутри runtime (`packages/runtime/src/workers/worker-loop.ts`) |
