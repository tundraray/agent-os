# Project Context

## Project Overview

- **Problem being solved**: Сотрудники компании вручную собирают данные из разрозненных систем (логи и метрики, Jira/Confluence, почта, календарь, документы) и вручную выполняют в них рутинные действия. Большие модели решают это хорошо, но дорого. Agent OS решает это моделями класса Haiku: качество достигается архитектурой агентов (декомпозиция, параллельные workflows, внешнее хранилище evidence, проверка выводов), а не размером модели.
- **Target users**: Сотрудники одной компании из разных отделов — аналитики, SRE и инженеры, менеджеры. Каждый пользователь видит только свои беседы и расследования. Доступ к инструментам и данным определяется его ролью.
- **Usage scenarios**:
  1. **Глубокий ресерч по данным**: расследование по источникам, объём которых больше окна модели (например, логи за период). Работа идёт через задачи, evidence и provenance (`docs/features/research-runtime/`).
  2. **Ресерч по документам и вебу**: сбор и сводка из Confluence, Google Drive и веба с привязкой каждого утверждения к источнику.
  3. **Рутинные действия в системах**: создать тикет, ответить на письмо, обновить запись через MCP-инструменты. Любое изменяющее действие выполняется только после явного подтверждения пользователя.
  4. **Чат-ассистент**: интерфейс в стиле ChatGPT — точка входа ко всем сценариям выше (`docs/features/chat-shell/`).

## Development Structure

- **Team composition**: Один разработчик. Claude Code — основной исполнитель: пишет код, документы и тесты. Разработчик принимает решения и утверждает документы.
- **Development phase**: Прототип. Готовы чат-шелл (беседы, история) и runtime расследований на fixture MCP с синтетическими логами. Продакшен-пользователей нет, реальные MCP-системы ещё не подключены.
- **Established conventions**:
  - Документы (PRD, UXRD, Design Doc, ADR, планы) пишутся на русском. Технические термины и код — на английском. Путь: `docs/features/{feature}/`, ADR — `docs/adr/`.
  - Требования нумеруются `FR-xx`, критерии приёмки — `AC-xx.y` в формате Given/When/Then с наблюдаемым исходом.
  - Коммиты на английском в формате Conventional Commits (проверяет commitlint), без строк атрибуции.
  - Исследовательская архитектура следует `docs/side_reserch/agent_os_workflow_spec.md` (workflows W1–W7, §17 — порядок сборки прототипа) и `docs/side_reserch/papers_digest.md`.

## Business Constraints

1. **RBAC на инструменты и данные**: агент вызывает MCP-инструмент или читает источник только при наличии у пользователя права на этот инструмент или источник. Изменяющий вызов (write) выполняется только после явного подтверждения пользователя в UI. Проверка: для каждого инструмента есть e2e-тест, в котором пользователь без права получает отказ, а источник не вызывается ни разу.
2. **Изоляция данных пользователей**: беседы, расследования и evidence одного пользователя недоступны другому. Проверка: каждый эндпоинт, отдающий пользовательские данные, покрыт e2e-тестом с двумя пользователями — 0 случаев доступа к чужим данным.
3. **Аудит действий агента**: каждый вызов инструмента записывается — пользователь, время, инструмент, аргументы, класс исхода (успех / пустой результат / ошибка инструмента / сбой транспорта / отказ по правам). Проверка: на каждый вызов инструмента в тесте приходится ровно одна запись аудита.
4. **Бюджет токенов**: у каждой задачи и каждого расследования есть явный бюджет. При исчерпании бюджета новые LLM-вызовы не запускаются, задача завершается с причиной «бюджет исчерпан». Проверка: тест с бюджетом меньше требуемого не выполняет ни одного вызова сверх лимита.
5. **Provenance фактов**: каждое утверждение в итоговом ответе ресерча ссылается на evidence — источник, инструмент, аргументы, срез данных, признак усечения. Утверждение без такой ссылки в ответ не попадает. Исключение (`docs/features/deep-research/prd.md`, FR-25): если в развёртывании не подключён ни один источник данных, ресерч идёт на знаниях модели — каждое такое утверждение явно помечено «из знаний модели, без источника», а пользователь предупреждён до запуска и в ответе.
6. **Качество на моделях класса Haiku**: цель — агентская схема (Haiku в рабочих ролях) отвечает не хуже одного агента на более сильной модели. Автоматического стенда оценки и эталонного набора нет (часть `eval` убрана решением пользователя 2026-11-01; может вернуться отдельной фичей), поэтому изменения агентского контура (промпты, декомпозиция, workflows) пользователь проверяет вручную на реальных задачах.
7. **Стоимость**: цель — расследование стоит не больше одного прогона той же задачи одним агентом на более сильной модели. Расход токенов и стоимость каждого вызова модели записываются в журнал токенов движка, поэтому стоимость каждого расследования видна; автоматического сравнения с базовой линией нет.

## Performance Requirements

- API списка бесед (200 бесед): p95 ≤ 300 мс; API сообщений беседы (100 сообщений): p95 ≤ 500 мс — на локальном Postgres.
- Время до первого токена в стриминге не хуже текущего каркаса + 50 мс.
- Отрисовка восстановленной беседы (50 сообщений): ≤ 1,5 с (p95).
- Рестарт процесса посреди расследования не теряет и не дублирует работу: все события доставлены, ни одно действие не применено дважды.

## External Integrations

- **Логи и метрики** (MCP, read-only): источник для расследований. Сейчас — fixture MCP с синтетическими логами (`docs/features/research-runtime/design-mcp-source.md`).
- **Atlassian — Jira, Confluence** (MCP): чтение тикетов и базы знаний, создание и обновление тикетов с подтверждением.
- **Google Workspace — Gmail, Calendar, Drive** (MCP): чтение писем, событий и документов, отправка и изменение с подтверждением.
- **Реестр MCP-серверов**: администратор подключает произвольные MCP-серверы и выдаёт права на каждый инструмент по ролям. Платформа не зашивает фиксированный список интеграций.
- **Дизайн-система**: файлы в репозитории — `docs/design-system/` (`README.md`, `foundations.md`). Главный UI-приоритет — комфорт при многочасовой работе: ограниченный контраст, без чисто белого и чисто чёрного. Визуальная проверка — в реальном браузере через Playwright.
